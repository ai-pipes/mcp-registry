# mcp-registry: guide for agents and contributors

Self-hosted MCP gateway: a Go server (DDD modular monolith, Postgres + pgvector, MCP) with a TypeScript web UI. The agent sees four meta-tools (`list_servers`, `search_tools`, `describe_tool`, `call_tool`), not the upstream tools. User-facing setup is in `README.md`; this file is the single source of rules for code changes (`AGENTS.md` points here). Releases up to 1.0.1 were a TypeScript server; 2.0.0 is the same product in Go, judged by the black-box compatibility suite against the published 1.0.1 (see "Compatibility suite").

## Layers inside a module

```
http    -> HTTP routes and handlers, input validation (httpx), the /mcp JSON-RPC handler (gateway)
app     -> use cases and queries; declares ports (repositories, UpstreamClient, Embedder, Clock, SecretBox...)
domain  -> aggregates, value objects, events, invariants. Plain Go: no I/O, no third-party packages
infra   -> port implementations: Postgres repositories (pgx), the OAuth client, OIDC, the embedders
```

Each module is `internal/modules/<m>/{domain,app,infra,http}` plus its root package (`internal/modules/<m>/<m>.go`), the module's public surface: other modules and the composition import only the root. `internal/kernel` is the shared kernel (errors, events, `Clock`, `AuditLog`, `SecretBox`, `UpstreamClient`, `Secret`, the JavaScript-compatible helpers). `internal/platform` is composition and cross-cutting infrastructure (config, db, migrate, outbox, httpx, logging, crypto, scheduler, upstream client, audit, and `app`: the wiring of every module and the operator CLI); no business logic there. `cmd/mcp-registry` is the entry (`--version`, `healthcheck`, the server, the CLI). `migrations/` holds the SQL files (package `migrations`, embedded).

The rules are machine-checked by `make go-verify` (`make go-arch-lint`, `golangci-lint` with depguard, `go test ./internal/archtest/...`). **A rule without a failing fixture does not count: add both together.** `internal/archtest` runs the real `.go-arch-lint.yml` against one violating fixture per rule in `internal/archtest/testdata/<rule>/` (`TestEveryRuleHasAFailingFixture`) and the Go-coded rules against theirs (`TestEveryGoRuleHasAFailingFixture`).

- `domain-is-pure`: `domain` imports only itself and `kernel` (go-arch-lint), and no `net`, `os`, `database/sql`, `io/fs` or `syscall` (`ImpureDomainImports`; `ImpureKernelImports` holds `internal/kernel` to the same, fixture `testdata/kernel-stdlib`).
- `application-only-domain`: `app` imports only itself, its `domain`, `kernel` and other modules' root packages.
- `no-inward-infra`: `domain` and `app` never import `infra`, `http` or `platform`.
- `modules-via-index`: another module is imported only through its root package (or reached through domain events in the outbox). A module's `http` may import its OWN root (the session guards and the principal live there; a root never imports its `http` or `infra`, so there is no cycle).
- `deps-only-in-infra`: `pgx`, `go-oidc` and the other drivers only in `infra` and `platform` (vendor rows of `.go-arch-lint.yml` and `depguard` in `.golangci.yml`, which also covers `crypto/*`); the MCP Go SDK only in `platform/upstream` (the upstream client); the JSON Schema library `santhosh-tekuri/jsonschema/v6` only in `gateway/infra`; `golang.org/x/term` only in the composition; the local embedder's libraries (`yalue/onnxruntime_go`, `daulet/tokenizers`, `golang.org/x/text`) only in `search/infra`.
- `migrations-only-platform`: the package `migrations` is imported only by the composition (`platform`) and the test support `platform/pgtest`.
- `platform-leaves`: the leaves `platform-{httpx,outbox,logging,db}` are what a module's `http` and `infra` may import from `platform`; `domain` and `app` never; the leaves import neither modules nor the composition. Every package belongs to exactly one component (`unattached-*-package` fixtures).
- `no-circular`: the Go compiler's.
- **Schema ownership.** Each module owns its database schema (`identity.*`, `catalog.*`, `connections.*`, `search.*`, `gateway.*`); other modules' tables are never read or written, not even in SQL joins. Cross-cutting tables live in `platform` (outbox, audit, migrations, key check). Checked by `ForeignSchemaRefs` (`internal/archtest/schema_ownership.go`): string literals in non-test Go files of `internal/modules/<m>/**` must not contain `<other module>.<table>`.
- **Secrets.** `PlainSecretFields` (`TestRepositoryHasNoPlainSecretFields`) and `SecretsIntoEmptyInterfaces` (`TestRepositoryPassesNoSecretToAnEmptyInterface`), see "Secret-carrying types" below.
- **Coverage.** `make go-cover`: `domain` and `app` of every module at least 90 % of statements, per package, from the unit tests alone (`internal/archtest/covergate.go`, `TestCoverageThresholdIsNinety`).
- Business rules live in `domain`, not in use cases: a use case only orchestrates ports and the domain.

The web UI and the contracts have their own rules (`pnpm arch`, dependency-cruiser, `.dependency-cruiser.cjs`): `no-radix`, `api-no-ui`, `no-circular`, each with a failing fixture in `apps/web/test/architecture/fixtures` (`apps/web/test/architecture.test.ts`, test project `arch`).

Layout: `cmd/mcp-registry`, `internal/{kernel,platform,modules/{identity,catalog,connections,search,gateway}}`, `migrations/`, `compat/` (the compatibility suite, its fakes, fixtures, goldens and schemas), `tools/notices`, `third_party/` (generated licence texts), `apps/web` (SPA), `packages/contracts` (zod schemas of the REST API; `make compat-schemas` exports them to `compat/schemas` for the suite), `e2e/` (Playwright: `csp.spec.ts` and the browser flows).

## Design decisions

- **Modular monolith.** One Go process, one repository, five modules with hard, machine-checked boundaries. Simple deployment and in-process transactions; a module can be split out later along existing boundaries. The cost is ceremony (ports, fakes in tests) even for simple cases.
- **Postgres without an ORM.** Postgres + pgvector is the only store; access through `pgx` and plain SQL, only in `infra` (and `platform` for cross-cutting tables). Row-to-aggregate mapping is written by hand. Migrations are versioned SQL files in `migrations/` (embedded by `migrations/embed.go`), applied at startup under an advisory lock (`internal/platform/migrate`) and recorded by file name in `platform.schema_migrations`: the files 0001-0010 are the ones 1.x applied, byte for byte; never edit an applied one. Integration tests run against real Postgres (Testcontainers, build tag `integration`, `internal/platform/pgtest`).
- **Transactional outbox.** Catalog writes domain events to `platform.outbox` in the same transaction as the aggregate change (`outbox.Append`); an in-process worker (`internal/platform/outbox`) delivers them (`FOR UPDATE SKIP LOCKED`) to subscribers (search). At-least-once delivery, so handlers are idempotent; retries with exponential backoff, after 10 attempts a periodic sweep takes over. Errors are stored as a neutral label, never message text (it may quote values). No message broker.
- **Local embeddings.** `Xenova/multilingual-e5-small` (q8, 384 dims, `passage: `/`query: ` prefixes) run by ONNX Runtime 1.30.0 through cgo (`yalue/onnxruntime_go`) with the tokenizer of `daulet/tokenizers`, baked into the image; every downloaded file (the library, the tokenizer archive, the model) is pinned by SHA-256 in `internal/modules/search/infra/onnx/native/pins.env` and fetched by `native/fetch.sh` / `native/fetch-model.sh`. The vectors equal those of 1.x (the reference ran the same model with transformers.js and the same ONNX Runtime build; see "Search" below for what parity needs). An OpenAI-compatible HTTP adapter sits behind the same `Embedder` port. Ranking is Reciprocal Rank Fusion over FTS and vector. Changing the model requires a full reindex and a vector dimension migration.
- **Search threshold.** Without a floor, vector search returns the whole index in some order and never says "nothing matches". A vector candidate passes only if cosine similarity >= `SEARCH_MIN_SIMILARITY` (default 0.83; FTS candidates are not filtered). Score = `rrf / (2 / (k + 1))`, `k = 60`, always in `(0, 1]`, not normalised to the best hit. Access and `hidden` filters are applied in the candidate query so `limit` is not eaten by inaccessible tools. Calibration on real Gitea (61) and YouTrack (23) tool lists: relevant queries scored >= 0.859, unrelated ones <= 0.809, so 0.83 sits in the gap with margin for q8 noise (~0.005). The sample is small; recalibrate for another model or corpus. Embeddings are computed one document per call: the q8 model uses one dynamic activation scale per batch, which shifts vectors by up to ~0.005 depending on batch neighbours.
- **Strict CSP.** `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; frame-ancestors 'none'`, emitted by `httpx.SecurityHeaders()` (`internal/platform/httpx/security.go`) on every response. No inline scripts or styles, no `unsafe-eval`, hashes or nonces. Pinned by `internal/platform/httpx/httpx_test.go`, `compat/platform_test.go`, `apps/web/src/app/csp.test.tsx`, `apps/web/src/components/Toaster.test.tsx`, `apps/web/src/zod-config.test.ts` and `e2e/csp.spec.ts`.
- **Upstream auth findings** (spike against `gitea-mcp` 1.11 in HTTP mode and YouTrack 2026.2 `/mcp`): both accept a person's OAuth access token per request (different people interleaved in one upstream process each see themselves), via `Authorization: Bearer {secret}`; both accept PATs with the same header; both answer an invalid token with HTTP 401, so `UpstreamClient` maps 401 to `UpstreamError` kind `unauthorized` with no special cases. Access tokens live 3600 s. Gitea issues a new refresh token on refresh but the old one keeps working unless `[oauth2] INVALIDATE_REFRESH_TOKENS=true`; Hub reuses the same refresh token and issues one only with `access_type=offline`. Gitea needs no scopes; Hub's scope is the YouTrack service ID. `tools/list` does not depend on the user, so syncing the catalog with an admin's token is correct. Single-flight refresh stays (it covers one-time refresh tokens and removes duplicate refreshes). `pat_user` remains as a fallback mode. Recorded `tools/list` fixtures: `compat/fixtures/tools/{gitea,youtrack}.json` (read by the compat fakes, the Go tests and the generators).

## Domain vocabulary

- **Server**: catalog aggregate. `slug` (kebab-case, tool-name prefix), name, description, upstream URL (Streamable HTTP), auth mode (`oauth_user` | `pat_user` | `shared_secret` | `none`), access (all permitted people or a list of groups), call timeout, daily limit per person, status (`active` | `disabled`).
- **Tool**: snapshot of an upstream tool (`tools/list`): name, title, description, `inputSchema`, `outputSchema`, annotations and a `hidden` flag set by an admin that survives sync. A hidden tool is neither searched nor callable.
- **ToolRef**: the agent-facing name `<server>.<tool>`, split at the **first** dot (upstream names may contain dots).
- **AuthMode**: how the gateway authenticates to the upstream: `none`, `shared_secret`, `pat_user`, `oauth_user` (+ `OAuthClientConfig`: authorize/token/revoke URL, client ID, scopes, `extraAuthorizeParams`, e.g. `access_type=offline` for Hub; they cannot override flow parameters such as `state`, `redirect_uri`, `scope`; scope `openid` is rejected since there is no discovery to verify an ID token); `header` and a `template` with `{secret}`. The header is built only by `HeaderFor` (`catalog/domain/auth.go`, exposed as `catalog.HeaderFor`).
- **Access / canUse**: who may use a server (`all` or groups): admins any active server, nobody a `disabled` one (`CanUse`, `catalog/domain/access.go`).
- **SecretBox**: encryption port (`kernel.SecretBox`); AES-256-GCM implementation `crypto.NewAESGCMBox` (`internal/platform/crypto/secretbox.go`; with `SECRETS_KEY_OLD` it also opens with the previous key, always seals with the current one). The server secret is stored only sealed in `catalog.servers.secret`; `ServerView` exposes only `secretSet`. **Secret reset** (`Server.Update`, `secretDestinationChanged` in `catalog/domain/server.go`): the stored secret is cleared (`secretCleared`, audit `server.secret_clear`) when the place it is sent to changes: auth kind, for `shared_secret` the upstream `url`, for `oauth_user` (the secret is the client secret) `tokenUrl`, `revokeUrl` or `clientId`; header, template, scopes, authorize URL and an `oauth_user` upstream URL keep it. `PUT /api/servers/:slug` takes no secret; the form sends `PUT .../secret` after it, so a secret entered in the same save is kept (`secretResetReason` in `apps/web/src/admin/servers/formModel.ts` only mirrors the rule for the warning before saving, and the form says afterwards that the secret must be entered again). **`SECRETS_KEY_FILE` / `PGPASSWORD_FILE`** (`internal/platform/config`, `config.Load` with its file reader): the value is read from the named file and trimmed (for Docker secrets and the quick start); a variable together with its `_FILE` twin is a startup error, an unreadable or empty file too; errors name the variable and the path, never the content. `PGPASSWORD_FILE` becomes `Config.DatabasePassword`, which the server passes to `pgx` over the URL's password.
- **Key check** (`internal/platform/crypto/keycheck.go`, all its SQL): `platform.key_check` (migration `0010_key_check.sql`, one row) holds a known text sealed with the key configured on the first start that has the check. `crypto.Verify` (verdict by the pure `crypto.Judge`) runs at start after migrations and before the modules' first-start hooks (`internal/platform/app/lifecycle.go`) and returns `created` / `ok` / `needs_rotation` / `mismatch`: absent -> created (also the first start after upgrading from 0.1.0); opens with `SECRETS_KEY` -> continue; opens only with `SECRETS_KEY_OLD` -> continue with a warning to run `rotate-secrets-key`; opens with neither -> one `fatal` record (never key material, with a pointer to the README section "Recovering from a key mismatch") and exit code 1. It proves the key is the recorded one, not that it opens the stored secrets, and it is an operational guard, not a security boundary. The server never generates or replaces the key itself. `crypto.Inspect` is the read-only judgement (the CLI never creates the check); `crypto.Remove` backs `reset-key-check`.
- **Key rotation (re-seal)**: `kernel.Reseal(sealed, from, to)` returns `current` (new key already opens it, so repeats are safe) / `resealed` / `unreadable`. Each module re-seals its own data through its own API: `ResealServerSecrets` (catalog root; `ReplaceSealedSecret` in `catalog/infra/pg_servers.go`, compare-and-set retried, 3 attempts in all, exhausted counts as `failed`; no `updated_at` or events) and `ResealConnections` (connections root; `ConnectionStore.ListKeys` + `WithLock`; `Connection.ReplaceSealed` keeps status, expiry and `updatedAt`). The check value is re-sealed by `crypto.ResealCheck` (platform; compare-and-set, `current` / `resealed` / `unreadable` / `absent`; a lost compare-and-set yields `current`): the CLI prints `key check: re-sealed` / `already current` / `none stored` / `cannot be read with either key`, records it in the audit and exits 1 when anything cannot be opened with either key (a server secret, a connection or the check) or a server secret's compare-and-set ran out of attempts, listing it under `error: neither key opens (left as they were):`. Run by CLI `rotate-secrets-key`.
- **Connection**: aggregate of `connections`: a person's credentials for a server, `kind` `oauth` (access + refresh + `expiresAt`) or `pat`; `status` `ready` / `expired` (no row = `needs_connection`, listed as `missing`). Tokens are held only sealed (table `connections.connections`). Domain rules (`connections/domain/connection.go`): `CredentialPlan` (refresh early when < 60 s to `expiresAt` or on `forceRefresh`; without a refresh token use until expiry; `expired` is not refreshed until reconnect; PATs never refresh), `Refreshed` (refresh token from the response, else the previous one), `Expire` (ready -> expired), `IsRefreshRejected` (expire only on an OAuth error from the token endpoint: `invalid_grant` or HTTP 400/401; timeouts, network errors and other 5xx store nothing; `invalid_client`/`unauthorized_client` with 401 mean the gateway's client credentials are wrong, not the person's: `unavailable`, nothing stored), `UsableWhileProviderDown` (provider down but the access token is unexpired and not rejected upstream: use it, else `unavailable`).
- **Server config fingerprint**: `ServerFingerprint` (`connections/domain/fingerprint.go`; the JSON array of 1.x byte for byte, since connections written by 1.x carry it): upstream URL, auth kind, authorize/token URL and client ID (not scopes or revoke URL), i.e. everywhere a token or code is sent. Stored on the connection (`issued_for`) and on pending connects. The revoke URL in force at issue time is stored separately (`connections.connections.revoke_url`, `Connection.MayRevokeAt`): `disconnect` revokes only there and only if it equals the current one. If an admin changes fingerprinted fields, the token is never sent to the new place: resolving expires the connection (`config_changed`), `Disconnect` deletes without revoke, `CompleteConnect` refuses (`invalid_state`).
- **ResolveForSending** (the single entry for a credential that will be sent; `connections.Service.ResolveForSending(ctx, userID, target, forceRefresh)`, `app.ResolveForSending` in `connections/app/resolve.go`): the raw secret (access token or PAT) or `needs_connection` / `expired` (reconnect) / `unavailable` (OAuth provider down, or the catalog target the caller read no longer matches the stored fingerprint: retry later). Refresh is single-flight per person, server and fingerprint in the process (`SingleFlight`, detached from the callers' cancellation, bounded at 30 s) plus `ConnectionStore.WithLock` (`select ... for update` in a transaction) across replicas; the decision is re-made under the lock and another process's fresh token is reused. **Only that row and the provider HTTP request (10 s timeout) happen under `WithLock`**: server config and client secret are read before the lock, audit is written after commit (otherwise the transaction waits for a second pool connection and the pool can deadlock). `MarkExpired` after an upstream 401: immediately for `pat_user`, for `oauth_user` only if a just-refreshed token is rejected too.
- **OAuth connect** (`connections/app/connect.go`): `StartConnect` (only `oauth_user` servers the person may use; PKCE S256, `redirect_uri = <PUBLIC_URL>/api/connections/callback`) -> **PendingConnect** (`connections.pending`: one-time `state`, 10 min, owned by the starter, bound to the fingerprint) -> `CompleteConnect`; `SavePAT` (only `pat_user`), `Disconnect` (deletes and calls revoke if allowed; revoke errors ignored), `ListConnections`. Ports in `connections/app/ports.go`: `OAuthClient` (`infra/oauth_client.go`, hand-written on `net/http`, no discovery, HTTP Basic client auth with form-encoded ID and secret per RFC 6749 section 2.3.1; token endpoint errors -> `TokenEndpointError{Status, Code}`), `ServerDirectory` (over catalog's root package), `ConnectionStore`, `PendingConnects`, `Pkce`. REST: `GET /api/connections`, `POST /api/connections/:server/start` -> `{ url }`, `GET /api/connections/callback` -> 302 to `/connections?connected=<server>` or `?error=<ConnectCallbackError code>`, `PUT /api/connections/:server/pat`, `DELETE /api/connections/:server`. Both browser callbacks (`/api/auth/callback`, `/api/connections/callback`) redirect with `internal` on unexpected errors instead of a JSON 500 (logged without the message). The callback reads the session itself and redirects with `?error=unauthenticated` without one.
- **Callback limitation (SameSite=Strict)**: the session cookie is `SameSite=Strict`, so the browser sends it on the redirect back from an OAuth provider only if provider and gateway are the same site: **https and the same registrable domain** (eTLD+1). A provider on another domain, on `http` with an https gateway, or with a cross-site IdP in the redirect chain yields `?error=unauthenticated`. Supporting those would need a Lax cookie binding the browser to `state`, as identity login does.
- **User / login (identity)**: a person from the OIDC provider (`oidc_sub`), no passwords. OIDC is optional: `OIDC_ISSUER`, `OIDC_CLIENT_ID` and `OIDC_CLIENT_SECRET` are all set or all unset (a partial set is a startup error naming the missing ones; an empty value counts as unset); without them people sign in with a **LoginLink**, `GET /api/auth/login` redirects to `/?loginError=oidc_not_configured`, and `/mcp` and `sk_` tokens never depend on OIDC. `GET /api/auth/login` -> provider (Code + PKCE, state in `identity.oidc_pending`, 10 min, one-time) -> `/api/auth/callback` -> session cookie (12 h idle, 30 days absolute: `SessionIdleTTL`, `SessionAbsoluteTTL`). Members of `OIDC_LOGIN_GROUP` or `OIDC_ADMIN_GROUP` (admins) get in; groups come from the `OIDC_GROUPS_CLAIM` claim (default `groups`; a list of names, or an object whose keys are the names, as Zitadel's roles) of the ID token, with UserInfo as fallback; the request asks for `OIDC_SCOPES` (default `openid profile email groups`, must include `openid`), and role and groups are refreshed on each login. `returnTo` is a relative path only. Anonymous load is bounded: a failed code exchange is counted per client IP (an in-memory limiter, `FailedCallbackAuditLimit` 20 per `FailedCallbackWindowSec` 60, `identity/domain/loginflow.go`) and past the limit `auth.login_failed` is not written, but the exchange is still attempted and a valid code always signs in; starting a login is never limited. `identity.oidc_pending` drops expired rows (`expires_at <= now()`, index `oidc_pending_expires_idx`) on every insert and never evicts an unexpired one (a cap would let an anonymous caller cancel other people's logins): the table is bounded by the start rate times ten minutes, not by a cap; bounding it for real needs the pending state in a signed cookie. Disabling a person deletes all their sessions and pending login links and revokes all their tokens (`SetDisabled`). `Principal` carries `groups`, `via` and `tokenId` (for `sk_`). Discovery is lazy (`identity/infra/oidc.go`, `OIDCProvider`; its HTTP client ignores proxy variables, as the other outbound clients and 1.x do): the server starts without the IdP, discovery happens on first login (5 s timeout), is cached after success and retried after failure; while the IdP is down login redirects to `/?loginError=idp_unavailable`, `/mcp` and tokens do not depend on it.
- **LoginLink**: a one-time sign-in code for one person, for installs without OIDC (and as break-glass access with it). `ll_` + 32 random bytes base64url, valid 15 minutes (`LoginLinkExpiry`), only its SHA-256 is stored (`identity.login_links`, `identity/infra/pg_links.go`) and the row is removed when used. A person has at most one live link: `IssueLoginLink` (`identity/app/loginlink.go`; existing enabled person only, audit `auth.link_issued`) deletes the earlier one; disabling a person removes their links; expired ones are pruned with expired sessions (`PruneExpiredSessions`, job `session-retention`). Link format `<PUBLIC_URL>/login#link=<code>` (`LoginLinkURL`): the code is in the fragment, which browsers do not send to the server. The SPA (`LinkLogin`) handles the fragment only on `/login`, strips it from the URL and sends `POST /api/auth/link` (`CompleteLinkLogin`): 204 + session cookie, or `invalid_link` 401 (unknown, expired and used are indistinguishable), `disabled` 403, `rate_limited` 429 with `Retry-After`; failed attempts are counted per client IP (fixed window of 60 s, in memory: the 11th failure locks that IP for 60 s and is answered `rate_limited` with `Retry-After`; a valid code is still accepted from a locked-out IP; failed `sk_` checks on `/mcp` have their own limiter, 30 per minute, and the failed-callback audit limiter allows 20 audited records per minute per IP). The SPA never sends a code without one explicit click, whatever the session state (no auto-send: closes login CSRF and the two-tab race): the card names the current account when signed in, and a rejected link whose session check then finds a session (another tab) lands in the app silently. A successful `POST /api/auth/link` that carried a session cookie ends that old session (`logout`) before the new cookie is set; a rejected link leaves it alone. The audit record of a refused consumed link names the person (`actorId`) unless they no longer exist. `GET /api/auth/methods` -> `{ oidc: boolean }` (public); without OIDC the sign-in page shows the `login-link` command instead of the SSO button. Audit: `auth.login` with `via: 'link'`; `auth.login_failed` only when a real link was consumed and then refused (unknown or malformed codes are not audited); the code is never written to audit or errors. A session from a link is an ordinary session; role and groups come from the stored person, and a link sign-in updates only `last_login_at`. Without OIDC there are no groups beyond what `create-user` assigns (login group or admin group): admins see every active server, members see servers open to `all` or to the login group. **First start without OIDC**: `BootstrapLocalAdmin` (`identity/app`) creates the admin `local-admin` when there are no people and issues a link (`NeedsBootstrapLink` in `identity/domain` decides `create` / `reissue` / `none`; two replicas on an empty database both provision, the first one's logged link may be dead, recovery is `login-link local-admin`); the identity wiring's first-start hook (`internal/platform/app/identity.go`) logs one `warn` record whose `url` field is the link. It logs a new link on every start (each invalidates the previous) until `local-admin` has signed in once, and never when OIDC is configured or any other person exists; a failure is logged as an error and does not stop the server.
- **ApiToken**: `sk_...` token; only its SHA-256 is stored, with `lastUsedAt`/`revokedAt`. Grants access to `/mcp` only, never to `/api/**`. Failed `sk_` checks on `/mcp` are limited per client IP (30 per minute; the 429 carries `Retry-After`, decided `token-429-retry-after`).
- **CallTool (gateway)**: `app.CallTool(ctx, deps, CallToolCommand)` (`gateway/app/calltool.go`) -> the upstream result as the gateway's domain projects it (`ProjectUpstreamResult`: `content`, `structuredContent` only when a plain object and `isError` only when defined; `_meta` and every other field dropped; a missing `content` becomes `[]`), or `isError: true` with a short text (`gateway/domain/texts.go`). Order: tool usable by the person now (`ToolCatalog.ToolFor`; hidden, removed, server disabled or closed -> one `not_found`, upstream not called) -> arguments vs `inputSchema` (`ArgsValidator`, `gateway/infra`) -> credentials (before the quota: an unconnected service spends no quota; `unavailable` -> "<Server> is unavailable.", `transport_error`) -> daily limit (`Quota.TryConsume`) -> `UpstreamClient.CallTool` with the header from `catalog.HeaderFor`. The arguments are forwarded as the bytes the agent sent. Upstream 401 (`OnUpstreamUnauthorized`, `gateway/domain/unauthorized.go`): `oauth_user` one forced resolve and one retry (quota not spent twice; a forced resolve that returns the rejected secret again is not sent: unavailable), second 401 -> `MarkExpired`; `pat_user` -> `MarkExpired`, no retry; `shared_secret`/`none` -> rejected text, `transport_error`. The validator is advisory (the upstream validates too); its bounds are under "Gateway" below. A failed call-log write never changes the agent's answer; `server`/`tool` in the log are cut to 200 characters.
- **CallOutcome**: `ok`, `upstream_error` (upstream `isError: true` or a JSON-RPC error to `tools/call`, `UpstreamError` kind `rejected`; the agent gets `<Server> rejected the call (JSON-RPC <code>): <upstream message, up to 500 chars>`, never logged), `timeout`, `transport_error` (network, 5xx, `too_large`, rejected server key, OAuth provider down), `denied:not_found` / `invalid_arguments` / `quota` / `needs_connection` / `expired`.
- **QuotaDay**: UTC calendar day `YYYY-MM-DD`, resets at the next UTC midnight. Counter `gateway.quota (user_id, server, day, count)` with an atomic `insert ... on conflict do update ... where count < limit returning`.
- **CallLogEntry**: `gateway.calls`: who, which token (`null` for a session), server, tool, start, duration, `CallOutcome`. No columns for arguments or results. `CallLog.List` (`gateway/infra/pg_calllog.go`): newest first (start time, then numeric id), filters `userId`/`server`/`outcome` and the cursor `before` (strictly older) or the pair `before` + `beforeId` (`(started_at, id) < (before, beforeId)`, no skipped ties; the web page sends both; `calls_started_at_idx` serves the range, no migration). Kept `CALL_LOG_RETENTION_DAYS`.
- **Search / index**: `search.documents` (ref, server, title, description, body, tsv, embedding), one row per visible tool. Indexed on catalog events `catalog.tools_changed` / `tools_removed` / `server_changed`, data only from the catalog root's `ListToolsForIndex`. Document text `"<server>. <description>\n<name> <title>\n<description>"`. If the embedder fails, a new document is stored without a vector (text search works) and `IndexMissingEmbeddings` (a sweep every 5 minutes) fills it later; a document that already has a vector keeps it (decided `vector-kept-on-failed-reembedding`).
- **searchTools / ToolHit**: `SearchTools` (search root, `search/app/search.go`; query, limit, servers) -> `{ ref, server, score }`: FTS + vector through RRF; vector failure is logged as warn and search falls back to text; the `servers` filter applies in SQL before `limit`, empty `servers` -> `[]` without a query. Access is decided by the caller (gateway).
- **Outbox**: event table written in the same transaction as the change (`outbox.Append`); a worker (`internal/platform/outbox`) delivers events to the handlers the modules register (`app.Module.Handlers`).
- **UpstreamClient**: port to upstream MCP (`kernel.UpstreamClient`, `internal/kernel/upstream.go`): `ListTools` (all pages), `CallTool`; errors are `UpstreamError` kinds `unauthorized` / `timeout` / `too_large` / `transport` / `rejected` (JSON-RPC error; code and text in the rejection, not the message). The target is URL + ready headers + timeout + response byte limit. Implementation `internal/platform/upstream` (the only importer of the MCP Go SDK): a new MCP session per operation, one timeout per operation, response bytes counted as a stream and the operation aborted on overflow, redirects refused, no proxy from the environment; messages never contain response bodies or credentials. Test upstream: `compat/fakes` (`StartUpstreamE`).
- **Catalog sync**: `SyncServer` (`catalog/app/sync.go`): upstream `tools/list` -> `ReconcileTools` -> `tools_changed`/`tools_removed`. `principal` is an admin (button) or `null` (scheduler). Credentials: `none` none, `shared_secret` the server secret, `oauth_user`/`pat_user` the personal secret of the sync owner (the admin who pressed sync, or `sync_user_id`, the last successful admin, for the scheduler). Rules in `catalog/domain/sync.go` (**SyncOwner**): `MayLend` (only while that person is an enabled admin, else `needs_connection`), `SyncFailureOfUpstream` / `FailureOfCredential`. Port **SyncCredentials** (`catalog/app/ports.go`) wired by `lateSyncCredentials` (`internal/platform/app/catalog_credentials.go`). On failure tools are unchanged and `last_sync_error` holds `SyncFailureText`. **SyncRecord** (`Server.ApplySync`, `SaveSyncState`): `last_sync_at` is the start of the last attempt; an older attempt never overwrites it; only a successful admin sync changes `sync_user_id`.
- **Catalog and admin REST** (session + `Origin`; Bearer -> 401; admin routes 403 for members before parsing the body, identity's `RequireAdmin` on the prefix). Server edits use optimistic concurrency: `catalog.servers.version`, the repository (`catalog/infra/pg_servers.go`) writes only at the read version, else `server_conflict` -> HTTP 409; the secret is written only when the aggregate changed it (`Server.SecretChanged`), so a concurrent `rotate-secrets-key` is not rolled back. `GET /api/catalog`; admin: `GET/POST /api/servers` (`POST` = `RegisterServer`: create + immediate sync; a sync failure does not undo creation), `GET/PUT /api/servers/:slug`, `PUT .../secret`, `POST .../status`, `POST .../sync` -> `{ added, changed, removed }` (`needs_connection` 400, `sync_failed` 502), `GET .../tools`, `PUT .../tools/:name/hidden`, `GET /api/calls`, `GET /api/audit` (newest first by the numeric id, `before` pages by it). Contracts in `packages/contracts/src/{servers,tools,calls,audit}.ts`; the suite validates every `ServerView` against the JSON Schema exported from it (`compat/schemas`). Body validation errors are 422.
- **MCP interface** (`internal/modules/gateway/http`): `/mcp` is a hand-written JSON-RPC handler (`mcp.go`, `classify.go`, `zodissues.go`; no MCP SDK on the server side), Streamable HTTP, both protocol eras on one address; guards in order: body limit (`MCP_MAX_BODY_BYTES`; the rest of HTTP 1 MiB) -> Host (`guards.go`, `PUBLIC_URL` host, localhost, 127.0.0.1 and `ALLOWED_HOSTS`) -> Origin -> bearer `sk_` token -> handler; capabilities exactly `{"tools":{"listChanged":false}}`. `tools.go` holds the four meta-tools (their set and schemas never depend on the catalog; `tools/list` + `instructions` < 8000 characters, pinned in `mcp_test.go`), `text.go` the instructions and `ShortDescription` (<= 200 characters, cut at a word); their use cases are `gateway/app/meta.go`. `search_tools` searches only servers the person may use and re-checks each hit with the catalog. Upstream URLs and auth settings are never exposed over MCP. Unexpected errors -> `Internal error.` (logged without arguments).
- **AgentConnection** (`AgentConnectionOf`, `gateway/domain/agent_connection.go`): what the agent learns about a server's connection: `not_required` (`none`/`shared_secret`), else `ready` / `expired` / `needs_connection`; the latter two get `connectUrl = <PUBLIC_URL>/connections` in `list_servers`.
- **Scheduler** (`internal/platform/scheduler`, jobs registered by the modules' wiring): `catalog-sync` (every active server at start and every `SYNC_INTERVAL_HOURS`; one failure is recorded and logged, the others continue; a shutdown cancels a running sync), `gateway-retention` (call log older than `CALL_LOG_RETENTION_DAYS`, quota counters older than yesterday UTC) and `session-retention` (identity: expired sessions and expired login links), each at start and then on its period. A failed run is logged and the schedule continues.

## Operator CLI

`cmd/mcp-registry` handles `--version` (prints the version, nothing else read) and `healthcheck` before the configuration; with no argument it starts the server, with a command it runs `app.RunCLI` (`internal/platform/app/cli.go`). In the image the CLI is `mcp-registry <command>` on the `PATH` (`docker compose exec app mcp-registry ...`). Exit codes: 0 / 1 operation failed / 2 bad invocation. Commands (each module registers its own in its wiring, `CLICommand{Name, Usage, Guard, Run}`; the usage text lists them in the fixed order of 1.x): `create-user --sub --name [--admin | --member]` (`ProvisionUser`, idempotent by `sub`; decided `create-user-keeps-role`: without a flag an existing person keeps their role), `create-token <sub> --name`, `login-link <sub>` (`IssueLoginLink`; prints the link as the only stdout line, exit 1 for an unknown or disabled person, 2 without a sub; works with OIDC configured too), `create-server --json <file> --as <sub> [--secret-env VAR]` (`ServerInput`, `RegisterServer`; the secret only from stdin, read without echo on a terminal, or a variable, never printed; decided `create-server-sync-exit`: exit 1 when the first sync fails), `sync <slug> [--as <sub>]`, `reindex` (`ReindexAll`; decided `reindex-wording`), `rotate-secrets-key` (audit `secrets.rotate`), `reset-key-check --yes` (`crypto.Remove`: deletes the stored key check so the next start records the configured key; without `--yes` exit 2; audit `secrets.key_check_reset`; prints `key check removed: ...` or `key check: nothing to remove`). Key guard: before a known command, the stored check is judged read-only against the configured keys (`crypto.Inspect`) by the command's `Guard`: `GuardWarn` (default) prints one `warning:` line on `mismatch` and proceeds, `GuardRefuse` refuses with exit 1 (`create-server`, the only command that seals a new secret), `GuardNone` skips it (`rotate-secrets-key`, `reset-key-check`). Details under "Module seams" and "Key commands" below. Tests: `internal/platform/app/*_cli_test.go`, `*_cli_int_test.go`, and the CLI scenarios of the suite (`compat/cli_*_test.go`).

## How to add a use case

1. Domain test first (`*_test.go` next to the code in `domain`): aggregate/value object invariants, red -> green. Domain rules go in `domain`, not in the use case.
2. Use case in `app` with fake ports in its test (no database, no Docker); declare the ports in `app/ports.go`. Keep `domain` and `app` at 90 % or more (`make go-cover`).
3. Port adapter in `infra` (Postgres through pgx, HTTP clients...), with an integration test (`*_int_test.go`, `//go:build integration`, a migrated database from `pgtest.StartMigrated`).
4. Expose it through the module's root package if another module or the composition needs it; HTTP in `http` (validation with `httpx.Fields`, errors through `httpx`).
5. Wire it in the module's file of `internal/platform/app` (routes, jobs, outbox handlers, CLI commands); never in a module.
6. If the change is visible over HTTP, `/mcp` or the CLI, a compat scenario judges it; a behaviour that differs from 1.0.1 needs an owner decision first (see "Compatibility suite").

A new module, term or command updates this file in the same change.

## Implementation notes

- **Secret-carrying types** (`internal/kernel/secret.go`). A plaintext secret, token, code, key or ciphertext held in a struct field (people's tokens and PATs, server and OAuth client secrets, session ids, `sk_` tokens, `ll_` codes, OIDC/OAuth state, code, verifier and nonce, sealed bytes) is a `kernel.Secret` (string) or `kernel.SecretBytes` ([]byte), never a `string`/`*string`/`[]byte`: both keep the value two unexported pointers deep, so fmt (any verb, any holding, an unexported field of another struct included), slog and JSON print `[Redacted]` (`[unset]` for the zero value, which means "not set"; `kernel.NewSecret("")` is a set empty secret, `config.NewSecret("")` is unset), and they are not comparable (`==` is a compile error; the gateway compares through the constant-time `SecretComparer`). The value is read only by `Reveal()`, at the boundary that sends, seals, hashes or stores it; wire formats that must carry it (the created token's response, a decoded request body) use a named DTO filled by `Reveal`, never a marshalling secret type, and SQL arguments and scan targets are plain values (a Secret passed where `any` is accepted compiles but never carries the value: pgx stores the marker and fmt prints it, silently; the check is `internal/archtest` `SecretsIntoEmptyInterfaces`, `TestRepositoryPassesNoSecretToAnEmptyInterface`, which type-checks the non-test code of `internal/` and `cmd/` under the default and `integration` tags (golang.org/x/tools/go/packages; `onnx` is not covered: its cgo files need the native libraries) and fails on any expression whose type is or holds `kernel.Secret`/`SecretBytes` converted to an interface with no methods (fmt, slog, pgx, json, `[]any`, `map[string]any`, `any` returns and assignments, multi-value calls `a, b = f()`, function values whose parameters or results hold a secret, and arguments bound to a type parameter whose constraint has no methods, unless the generic function is declared in the same package and its body never lets a value of its type parameters reach an empty interface; generated files are scanned too); interfaces with methods (ports) stay legal; fixtures `secret-into-any` and `secret-into-any-allowed`, registered with the other Go-coded rules in `TestEveryGoRuleHasAFailingFixture`). `config.Secret`/`SecretBytes` are aliases of the kernel types and `crypto.Keys` holds two `kernel.SecretBytes`. `kernel/secrettest` (`AssertUnprintable`) checks a value in 15 holdings x 12 verbs, slog text and JSON and `json.Marshal`; each package that holds secrets has a `TestSecretCarryingTypesAreUnprintableHoweverHeld`. Reflection-based printers in a failing test's output (testify diffs, go-cmp with an exporter) follow unexported pointers and can print a revealed value: never put a revealed secret into such an assertion or its message. Guard: `internal/archtest` `PlainSecretFields` fails `TestRepositoryHasNoPlainSecretFields` for a struct field (or named type) of `internal/` whose name ends with a secret word (`...Token`, `...Secret`, `Code`, `State`, `...Verifier`, `Nonce`, `Password`, `...Key`, `Authorization`, `...Link`/`LinkURL`, `SessionID`, `Sealed`...) and whose type is a plain string or byte slice, unless `plainSecretAllowlist` names it with a reason (error codes, wire DTOs, the fake IdP); fixtures `testdata/plain-secret-field` (reported) and `plain-secret-field-allowed`; a stale allowlist entry fails too.
- **Third-party notices** (`THIRD_PARTY_NOTICES`, `third_party/`, `tools/notices`). The image ships in `/usr/share/licenses/mcp-registry/` the project `LICENSE`, `THIRD_PARTY_NOTICES` (the hand-written overview: every component and where its texts are, plus the notices no licence file carries) and `third_party/`: `go/NOTICES` (every module `cmd/mcp-registry` links with `-tags onnx` on linux/amd64 and linux/arm64, with its licence files, and the Go standard library's licence), `onnxruntime/{LICENSE,ThirdPartyNotices.txt,SOURCE}` (from the PyPI wheel of the same ONNX Runtime release, pinned as `ORT_NOTICES_WHEEL_URL`/`ORT_NOTICES_WHEEL_SHA256` in `pins.env`; `SOURCE` holds the files' SHA-256), `tokenizers/NOTICES` (the Rust crates linked into `libtokenizers.a`: normal dependencies of `tokenizers-ffi` without proc macros and their subtrees, from a checkout of the pinned tag) and `web/NOTICES` (`pnpm licenses list --prod --filter @mcp/web`). All generated by `go run ./tools/notices go|web|rust <checkout>|onnxruntime` (identical texts written once and referred to afterwards); nothing is fetched at image build time. `tools/notices` tests (in `go test ./...`, so in `make go-verify`): `TestEveryLinkedGoModuleIsInTheNotices` and `TestGoNoticesAreCurrent` (a Go dependency update fails until the file is regenerated), the ONNX Runtime files against the pins and their hashes, the tokenizers file against the pinned tag, every direct dependency of `apps/web` at its version, the web file's `Inputs:` hash of the `pnpm-lock.yaml` entries it was made from (the importers `apps/web` and `packages/contracts` and the package and snapshot entries of every listed package, so a moved transitive dependency fails `TestWebNoticesFollowTheLockfile`), and the overview naming each file. Regeneration recipe in `CONTRIBUTING.md`.
- **Module seams** (`internal/platform/app`, `internal/platform/httpx`). Modules never import the composition; each module's wiring lives in `internal/platform/app` (one file per module, e.g. `identity.go`), calls the module's `infra`, `http` and root packages, and returns an `app.Module{Routes, Prefixes, Jobs, Handlers, Emits, Sweeps, FirstStart, BeforeServing, Closers, Commands}`; command bodies live there too. `modules(rt Runtime) []Module` (`app/module.go`) is the one list the server and the CLI both build; `Runtime` (Config, Pool, Logger, Clock, Audit, Box, Version) is what that wiring reads plain values from, and since the CLI builds every module for every command a module constructor must stay cheap (no I/O, no goroutines). Reproduced as the reference has them, not fixed: a server secret whose compare-and-set is lost three times is listed as unreadable (Q1), a key check whose update hits no row is `already current` (Q2), and a server disabled between the gateway's target read and the secret read still gets that one call. Deviations are in `CONTRIBUTING.md`.
- **The image** (`Dockerfile`, last stage `runtime`, the default target): stages `web` (Node 22 and pnpm, `pnpm install --filter '@mcp/web...'`, builds `apps/web/dist`; the only stage with Node), `model` (`native/fetch-model.sh`, the pinned model, on the build platform), `go-native` (`native/fetch.sh`, the pinned native libraries for the target architecture), `go-build` (`CGO_ENABLED=1 -tags onnx`, natively per architecture, `-X main.version=$VERSION`) and `runtime` on `debian:bookworm-slim` (glibc, `ca-certificates`, `libstdc++6`, `tzdata`; the setuid and setgid bits removed): user and group 1000 (1.x's uid, so an operator's 0400 secret file owned by 1000 keeps working; no home, nothing writable needed, everything under `/app` and `/usr/local` root's and read-only), `/usr/local/bin/mcp-registry`, ONNX Runtime at `/usr/local/lib/libonnxruntime.so.1` (its SHA-256 checked again at that path), the model in `/app/models` (the default `MODEL_DIR`), the UI in `/app/web`, the licences in `/usr/share/licenses/mcp-registry/`, `ENV MALLOC_ARENA_MAX=2`, OCI labels, `EXPOSE 3000`, `STOPSIGNAL SIGTERM`, `HEALTHCHECK --interval=10s --timeout=5s --start-period=30s --retries=3 CMD ["mcp-registry", "healthcheck"]` (1.x's timings), `CMD ["mcp-registry"]` in exec form (the server is PID 1 and handles SIGTERM itself within its 10 s limit; both compose files set `stop_grace_period: 15s`), no `ENTRYPOINT` (the suite replaces the command to run the CLI). Every `FROM` is pinned by digest. Stages `smoke-go-build`/`smoke-go` build the test-only programs of `scripts/smoke.sh` (`compat/cmd/smoke-upstream`, `compat/cmd/smoke-client`, `-tags compat`); nothing of them reaches the runtime image. About 300 MB.

## Compatibility suite

`compat/` is the black-box suite the server is judged by: scenarios (`compat/*_test.go`, build tag `compat`, package `compat_test`), the harness (`compat/harness`), fakes (`compat/fakes`: upstream MCP servers, OAuth providers, an OIDC provider), the recorded tools (`compat/fixtures/tools`), goldens (`compat/golden`), the JSON Schemas of the REST contracts (`compat/schemas`, `make compat-schemas`), the smoke programs (`compat/cmd`), the browser-flow orchestration (`compat/e2e`) and the self-check (`compat/selfcheck`). It runs IMAGES: the image under test and, for what depends on the machine, the reference.

- **Images.** The image under test is `COMPAT_IMAGE`, default `mcp-registry:compat` (`make compat-image`: the Dockerfile's default target built from this tree, the image a release ships; its `--version` must equal `VERSION`), its CLI `COMPAT_CLI`, default `mcp-registry`. **The image under test must start the server with its default command (`CMD`, not `ENTRYPOINT`: the harness runs the CLI in the same image by replacing the command) listening on port 3000.** The reference is the published TypeScript 1.0.1 pinned by the digest of its multi-arch index (`REFERENCE_IMAGE` in the `Makefile`, `defaultReferenceImage` in `compat/harness/stack.go`, the default base of `compat/selfcheck/Dockerfile`, kept equal by `TestTheReferenceIsPinnedByDigestTheSameEverywhere`; its CLI is the constant `node dist/cli.js`, `REFERENCE_CLI` in the `Makefile`, `harness.ReferenceCLI()`); `make compat-reference` pulls it and checks the digest, the harness never pulls. The upgrade source is the published 1.0.0 pinned by digest (`UPGRADE_FROM_IMAGE`, `make compat-upgrade-from`, CLI `node dist/cli.js`; `TestUpgradeSourceIsThePublished100PinnedByDigest` keeps it in one place).
- **Targets.** `make compat`: the whole suite (`./compat/...`, `-p 1`, packages one after another) against `mcp-registry:compat` with every decided deviation and `COMPAT_UPGRADE_FROM` = the published 1.0.0 (a real upgrade; `make compat COMPAT_UPGRADE_FROM=` makes it a restart test). `make compat-reference-run`: the same suite with the reference under test, setting `COMPAT_IMAGE`, `COMPAT_CLI='node dist/cli.js'`, `COMPAT_FIXED=` (none) and the upgrade source with its CLI explicitly, so every reference branch stays asserted and the vector and ranking comparisons are determinism checks. CI runs both on arm64 and amd64 (jobs `compat`, which also runs `make go-test-onnx-parity`, and `compat-reference`). `COMPAT_ARGS='-run ^TestPlatform'` runs a subset (patterns per area in `CONTRIBUTING.md`), `COMPAT_PKGS` picks the packages. Variables: `COMPAT_UPGRADE_FROM` / `COMPAT_UPGRADE_FROM_CLI` (the old image of the upgrade scenario and its CLI; default the image under test), `COMPAT_REFERENCE=1` and `COMPAT_REFERENCE_IMAGE` (see the compat rules), `SELFCHECK_BASE` (the base of the self-check image), `E2E_PLAYWRIGHT_ARGS` (flows). `go-verify` lints and vets the suite with `-tags compat` and runs its Docker-free tests by name, but does not boot a stack. Opt-in variables: `COMPAT_LOG_DIR=<dir>` (a stack whose test failed, or that failed to boot, writes its app container's log, secrets removed, to `<dir>/<test name>-<stack id>.log`; CI uploads the directory on failure) and `COMPAT_APP_ENV=NAME=value,...` (non-secret variables added to the app container's environment; the self-check passes `BREAK` this way; variables the harness owns, such as `DATABASE_URL` or `PUBLIC_URL`, are refused; log files and failure tails also have `ll_`/`sk_` values removed).
- **Compat rules.** A scenario or golden changes only together with confirmation against the reference image (1.0.1), never to make the server pass: a new subtest is first proven on the reference (`make compat-reference-run`), a decided deviation gets both branches, and a mechanical change (a wait bound, a helper) must pass on the reference too. The exception is a release of the reference itself: the scenario then judges the new behaviour strictly, and a deviation the release satisfied is removed from the registry. Goldens are rewritten only with `make compat-reference-run COMPAT_REFERENCE=1 COMPAT_PKGS=./compat/ COMPAT_ARGS='-run ^<the scenario that owns it>$$ -update'` after `make compat-reference`; the harness refuses `-update` unless `COMPAT_REFERENCE=1`, the image under test is the reference image (the default pinned one, or exactly `COMPAT_REFERENCE_IMAGE`, which must then be pinned by digest, `@sha256:<64 hex>`) AND `COMPAT_FIXED` selects no deviation (`CheckUpdateAllowed`, `compat/harness/golden.go`); `make compat` does not set `COMPAT_REFERENCE`; restrict it to the one scenario, since `-update` is global. A behaviour that 2.x changes on purpose needs the owner's decision and a deviation (or a new reference release); it is never recorded from the image under test.
- **Vectors and rankings are not committed.** q8 vectors differ between CPUs of the same architecture by up to about 0.015 (goldens recorded on an Apple Silicon Mac failed on the GitHub arm64 runner: 39 of 84 vectors differed), so both comparisons are made at test time against the reference image on the same machine (`harness.ReferenceImage`: `COMPAT_REFERENCE_IMAGE`, else the pinned default; it must exist locally, `make compat-reference`, otherwise the test fails naming that command and the variable). `TestSearchStoredVectors` runs `compat/golden/gen-embeddings.mjs` (`@huggingface/transformers` used directly, not the server's code) inside a container of the reference image (`harness.RunInReference`, `--network none`, the script mounted read-only) on the 84 passages the scenario indexes and compares the vectors stored in `search.documents.embedding` within 1e-6 (a vector perturbed by 1e-4 must be caught). `TestCatalogSearch/the_recorded_queries` boots a second stack from the reference image with the same fixtures and requires the same refs in the same order and scores within 1e-6; the CPU-independent assertions (score range, order, limit, nothing for unrelated queries) and literal first hits for the queries whose first hit was identical on every machine seen (so two images broken the same way are not accepted) stay in the scenario. With the reference under test these comparisons are determinism checks; with the image built from this tree they are the real comparison. `make go-test-onnx-parity` compares token ids and vectors of 1287 committed texts with the reference image's Node in containers of the same architecture.
- **Decided deviations** (`COMPAT_FIXED`, `compat/harness/deviations.go`: the `Deviation` constants and the registry `AllDeviations`, the source of truth). Twelve behaviours of the reference (1.0.0, unchanged in 1.0.1) that the server must NOT reproduce, decided by the owner: `create-user-keeps-role`, `create-server-sync-exit`, `ready-before-serving`, `oauth-state-kept`, `reindex-wording`, `request-id-on-refusals`, `config-errors`, `audit-login-via`, `token-429-retry-after`, `oidc-binding-kept`, `vector-kept-on-failed-reembedding`, `stale-removal-rechecks-catalog` (old -> decided, per id, in the table of `CONTRIBUTING.md`; the ID token's signature check is decided too but has no suite branch). Each has a `harness.Deviation` constant, an entry in `AllDeviations` and, in the scenario that touches it, two expectations: `if s.Fixed(harness.DevX) { decided } else { reference, unchanged }`. `COMPAT_FIXED` is `all`, a comma-separated list of ids or empty (an unknown id fails the stack start); **unset means all** (the image built from this tree), and the reference runs with it set and empty (`make compat-reference-run`): every reference branch must pass there, never weakened. A decided behaviour has no golden (it cannot be recorded from 1.0.x): its branch asserts exit code, effect and the stated texts. A Docker-free test fails when an id in `AllDeviations` has no `Fixed(harness.DevX)` call in a `compat/*_test.go` (a mention in a comment does not count). The fixed branches were proven against the reference image: a `COMPAT_FIXED=all` run against it fails exactly at the deviation sites, each with that deviation's own reason, and nothing else fails. `MODEL_DIR` pointing at a missing model must still start healthy and search by text (`TestConfigModelDirMissing`). Adding a deviation needs the owner's decision. The accepted differences (not decisions: logs, limits, wording, corner cases of parsing) are recorded in `CONTRIBUTING.md`.
- **Compat harness rules learned the hard way.** The harness transport drops idle connections after 1 s (`IdleConnTimeout`, `compat/harness/client.go`; the control API client of `compat/e2e` uses the same transport through `harness.NewHTTPClient`): the reference image closes idle keep-alive connections after 5 s, and a POST that meets a connection the app is closing dies with `EOF` (net/http never retries it); reproduced with `docker pause` in `compat/harness/keepalive_internal_test.go`. No scenario asserts `/healthz` right after a start or restart (the reference image blocks its event loop while it loads the embedding model, so `/healthz` can answer 503 under load): use `Stack.Answers` (`GET /` with `Accept: text/html`, the UI shell of the platform layer, status only); `/healthz` itself is asserted only by `TestPlatformHealthz` (the canary), the `healthz` row of the security-headers table and the `ready-before-serving` fixed branch (each after real work such as a sign-in, which ends a post-boot stall). Waits are bounds, not expectations: the outbox delivery of a whole recorded catalog waits up to 60 s (`catalogWaitDelivered`; 15 s timed out on loaded hosts on either image). Required security headers: `Content-Security-Policy`, `Strict-Transport-Security`, `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy`, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, each exactly once with its value; `Server` and `X-Powered-By` must be absent (they disclose the stack: a deliberate security requirement); other headers a framework adds are neither required nor asserted absent. The reference image sometimes ends with exit code 137 when it is stopped within seconds of first answering healthy (cause not established), hence there is no stop scenario. The Docker-free tests of `compat/` and `compat/harness` run in `make go-verify` by name (a new one is added to the Makefile line; none may boot a stack).
- **What the switchover scenarios prove.** `TestUpgradeKeepsEverything` (from the published 1.0.0 under `make compat`): the old image creates servers of every auth kind with their secrets, a member's PAT and OAuth connection, an `sk_` token, an indexed catalog, the call log and quota, audit records, a pending sign-in link and the unusual rows of `compat/handover_edges_test.go`; the image under test takes over the same database with no reindex, reconnect or new token, every credential reaches its upstream, an expiring access token is refreshed with the STORED refresh token, search returns the same refs and scores and `search.documents` is byte for byte the same, and its last subtest rotates the key with the CLI of the image under test and starts on the new key alone. `TestPlatformStartsOnReferenceDatabase` (the reference creates, the image under test takes over: healthy, no migration applied, key check untouched; another key and an unknown migration refused with exit 1 and one fatal record) and `TestPlatformReverseHandOver` (the rollback: the image under test creates, the reference takes over, applies nothing, leaves the key check byte for byte, and ends with a key rotation by the reference's CLI of what the image under test sealed) hand over people, session cookies, API tokens, connections (the stored fingerprint compares equal; the rows of `compat/handover_edges_test.go`) and a `shared_secret` server with a hidden tool, in both directions. `TestPlatformWithoutPeople` judges the platform layer with no person, session, token or CLI.
- **Suite self-check** (`make compat-selfcheck`, tag `selfcheck`, `compat/selfcheck/`, about 4-5 minutes): builds `mcp-registry:compat-broken` from the reference image (the published 1.0.1, which carries the Node the proxy needs; `SELFCHECK_BASE` overrides it; the target pulls it first) and runs the scenarios against it with the reference CLI and an empty `COMPAT_FIXED`, never inheriting the caller's `COMPAT_IMAGE`, `COMPAT_CLI`, `COMPAT_FIXED`, `COMPAT_REFERENCE`, `COMPAT_APP_ENV` or upgrade source (`ownedEnv` in `selfcheck_test.go`). `entrypoint.sh` runs the app alone when `BREAK` is unset; with `BREAK` set it starts the app on another port and a dependency-free Node proxy (`proxy.mjs`) on the public one, and the container ends as soon as either child does (a dead proxy exits 1; otherwise the app's exit code). The proxy applies one distortion: `csp`, `origin`, `extra-field`, `status`, `mcp-desc`, `www-auth`, `audit-drop`, `token-in-list` (`passthrough` = no distortion). `selfcheck_test.go`: two controls that must pass (no proxy, which only shows the derived image works and is not a control for the distortion runs; `passthrough`, which skips only the 10 MiB body-limit subtest, because the proxy mishandles that early refusal in a minority of runs, cause not fixed, see `proxy.mjs`), each requiring `--- PASS` for every named subtest; then per distortion one run in which the named subtests must print `--- FAIL`, the output must match a reason pattern only that distortion produces, a canary (`TestPlatformHealthz`) must pass in the same run and the stack must have booted. It proves the scenarios can fail on their reference branches; the decided branches are proven by the `COMPAT_FIXED=all` run against the reference. A distortion that no scenario catches is a gap in the suite: fix the suite, not the self-check. Workflow `compat-selfcheck.yml`: daily and manual, arm64. A new distortion is a new entry in `proxy.mjs` and in `selfcheck_test.go`.
- **Load comparison** (`make load-compare`, `compat/load_test.go`, build tags `compat load`; not run by `make compat` or `go-verify`, which only vets it): one stack per image, one after another (A = `UPGRADE_FROM_IMAGE`, B = `mcp-registry:compat`; `LOAD_IMAGE_A/B`, `LOAD_CLI_A/B`, `LOAD_FIXED_A/B`, `LOAD_OUT`), the same fixtures (recorded Gitea and YouTrack tools, an echo tool on a fake upstream with a 5 ms delay), reporting idle memory, sequential p50/p95/max and 50-concurrent rounds as a Markdown table. It asserts nothing except that a stack boots and answers no error under no load. See `CONTRIBUTING.md`, "Load comparison".
- **Browser flows** (`make e2e-flows`, build tags `compat e2e`, `compat/e2e/` and `e2e/flows/`; about a minute after the image is built; `make compat` does not run it): the real web UI in Chromium against the real application image `COMPAT_IMAGE` (default `mcp-registry:compat`, every decided deviation): thirteen flow specs plus the guard's self-test, `e2e/flows/00-12` and `08b` (first start link, OIDC return, token shown once, server form and its errors, hiding a tool, edit conflict, OAuth connect, permissions, disabling a person, session expiry, deep links; `e2e/csp.spec.ts` stays the CSP check). `TestBrowserFlows` boots three stacks (no OIDC; with the fake IdP; one whose public address is `http://gateway.compat.test:<port>` with its OAuth provider at `idp.compat.test`, the same site, which the connect flow needs because the session cookie is `SameSite=Strict`) and the fakes, starts the control API and runs `pnpm exec playwright test -c e2e/flows/playwright.config.ts` (own config, Chromium only, one worker, no retries; the existing `e2e/playwright.config.ts` ignores `flows/`). Chromium maps `host.docker.internal` and `*.compat.test` to 127.0.0.1 through `--host-resolver-rules` (`E2E_HOST_RESOLVER_RULES`). Both fake OAuth providers show a consent page (`fakes.WithConsentPage`): a provider that redirects at once leaves the gateway as the navigation's initiator and hides the `SameSite=Strict` difference, so `08-connect` (same site, connects) and `08b-connect-cross-site` (other site, `?error=unauthenticated`) only differ with the click. **Control API** (`compat/e2e/control.go`, client `e2e/flows/control.ts`): bound to 127.0.0.1 on a random port, every request needs the run's random bearer token (otherwise 401, unit-tested), and it knows only fixed operations with typed parameters, validated and refused on unknown fields: `GET /stacks`, `POST /cli/create-user`, `/cli/login-link`, `/stack/first-start-link`, `/idp/next-login`, `/servers` (registers a server of a given auth kind on a new fake upstream through the admin REST API), `GET /upstream/calls`, `POST /sessions/expire` (a fixed `update identity.sessions set last_seen_at ...`: like the compat suite's time travel it assumes the server under test keeps that schema, which the migration plan requires) and `GET /audit` (read-only, parameterised, filters by actor sub and action, an error rather than a silent cut past 500 rows; flows read specific records here, by actor and action) and `POST /echo` (returns the posted text, for the guard's self-test). No free-form SQL or CLI arguments. The control API's own tests (`TestControl*`) run in `make e2e-flows`; the Docker-free `TestControlRefuses*` and `TestControlEcho*` (token refusal, parameter checks) and `TestPlaywrightArgs*` also run in `make go-verify`. `make e2e-flows` fails when Playwright ran no test; `E2E_PLAYWRIGHT_ARGS` (a spec file) selects flows, `--list`, `--pass-with-no-tests`, `--retries*`, `--grep-invert*`, `--shard*`, `--last-failed`, `--only-changed*`, `-c` in any form (`-c path`, `-cpath`, `-c=path`), `--config*` and `--reporter*` are refused. Every spec runs under the shared fixture (`e2e/flows/fixtures.ts`): no `console.error`, page error or CSP violation (Chromium's own "Failed to load resource ... 401" lines are excused only per named status, path and, where given, page, `guard.excuseRefusal`), no sign-in link code or API token in a response URL, header (the raw ones too, with Set-Cookie) or body (every response the browser received is scanned, or listed as not scanned with a reason, or fails the test: `e2e/flows/guard.ts` holds the state machine. The guard owns page creation, so the capture (a DevTools session with `Network` and `Page` enabled and acknowledged) exists before a page's first request; Playwright's own response events are cross-checked against the records of the same page at the end (`response never captured` fails). Bodies are read when the browser reports the request finished, base64 bodies are decoded and scanned, binary asset types (SVG is text and scanned) and cache-served app assets whose read fails are listed, and a read that fails or never finishes is excused only by a NEW-DOCUMENT commit of its frame (not a history route change, not a navigation that has started: Chromium holds the read until the commit, or answers it when the navigation ends without one) or a closed page (judged on the facts at the failure; after a refused read that nothing else explains, only the close event is awaited within the grace), and then listed. A secret registered with `guard.secret` (also the login-link code `signInWith` uses) is looked for in EVERY response of the test, also those received before it was registered; only the body of the one response declared to carry it (page + method + path, at most once: a token's `POST /api/tokens`) is exempt. An `/api/` body lost while a secret is registered fails unless the flow declares exactly that loss with `guard.allowLostBody(page, method, path, why)` (a new-document loss only). `00-guard-selftest.spec.ts` covers every transition (T1-T9, N2, N3, the scans S, H, U) and that no spec creates a page behind the guard; a leak is also proved through the real network with the control API's `POST /echo`), and a secret shown in a dialog (`guard.secretGone`) absent from the DOM and the storages. Specs take texts from `apps/web/src/strings.ts` and role-based locators. Failed runs keep traces and screenshots in `node_modules/.cache/playwright/flows-results` (`E2E_OUTPUT_DIR`). CI job `e2e-flows` (arm64, after `go`, `make compat-image` first) uploads them with `COMPAT_LOG_DIR`.

## Running locally

- Tests: `pnpm install`, then `make go-verify` and `pnpm verify`. Docker is required for `make go-verify` (the integration tests start Postgres through Testcontainers) and for everything that runs the image.
- Server build: `make go-build` produces `bin/mcp-registry` (version from `VERSION`) without the local embedder (search is text-only and the server logs `search: local embedder unavailable, ...` with reason `not_built`). It needs Postgres with pgvector and `DATABASE_URL`, `PUBLIC_URL`, `SECRETS_KEY`; it serves the UI from `/app/web` (absent outside the image: use `pnpm dev:web`, which proxies `/api` and `/mcp` to `localhost:3000`). The embedder needs cgo, `-tags onnx`, the native libraries (`make native-libs`, `.cache/native/<platform>/`) and the model (`make native-model`); the image has all of them.
- Full box: `cp .env.example .env`, fill in `POSTGRES_PASSWORD`, `SECRETS_KEY` (`openssl rand -base64 32`) and, optionally, `OIDC_*`, then `docker compose up -d --build` (the Dockerfile's default target); check `curl localhost:3000/healthz`.
- Quick start: `quickstart.compose.yml` (project `mcp-registry`, image `${MCP_REGISTRY_IMAGE:-ghcr.io/ai-pipes/mcp-registry:1}` (the release that ships 2.0.0 moves the default to `:2`); `docker-compose.yml` is the build-from-source file and never names the published image). Services: `init` (one-shot, generates `secrets_key` and `pg_password` into the `secrets` volume only when absent or empty, files 0444, atomic write), `db` (`POSTGRES_PASSWORD_FILE`; Postgres not published) and `app` (`SECRETS_KEY_FILE`, `PGPASSWORD_FILE`, no OIDC by default: first-start sign-in link in the log). Data is in `pgdata`; `down -v` destroys data and key together, and losing `secrets` while keeping `pgdata` also changes the database password. Optional settings (OIDC, `TRUST_PROXY`, `COOKIE_SECURE`, limits, search, `LOG_LEVEL`...) pass through from the caller's shell or `--env-file` as `NAME: ${NAME:-}` (empty = unset), so shell variables of the same name apply. `SECRETS_KEY`, `DATABASE_URL` and `PGPASSWORD` are owned by the file, except `SECRETS_KEY_OLD` which passes through for key rotation (new key written into the `secrets` volume, old one in `SECRETS_KEY_OLD`; procedure in the README). The port is published as `${BIND_ADDRESS:-127.0.0.1}:${PORT:-3000}:3000` (localhost by default; `BIND_ADDRESS=0.0.0.0` with a real `PUBLIC_URL` behind HTTPS exposes it) and `PUBLIC_URL` defaults to `http://localhost:${PORT:-3000}`. The session cookie stays `Secure` by default: Chrome and Firefox accept it on `http://localhost`, Safari and plain http on a LAN address need `COOKIE_SECURE=false`; anything beyond localhost belongs behind HTTPS. Commands for a stack started from stdin: `docker compose -p mcp-registry logs app | grep "one-time link"` (link), `docker compose -p mcp-registry exec app mcp-registry <cmd>`, `docker compose -p mcp-registry down`. `up -d` succeeds even when the app loops on a key mismatch: check `logs app`.
- Quick start smoke test: `bash scripts/quickstart-smoke.sh` (project `mcp-quickstart-smoke`, port 38081, image built from this tree, or `QUICKSTART_IMAGE=<image>` for a prebuilt one that is left in place; `QUICKSTART_CLI` is the CLI command inside the app container, default `mcp-registry`; also checks the `starting` record and the newer-database refusal; unsets every variable the compose file passes through; compose fed through stdin; one sign-in link in the log, sign-in, token, `/mcp` `tools/list`; restart keeps the token and logs no new link; `compose()` passes `--env-file /dev/null` (a `.env` in the repo root cannot change the run); the documented file-less `login-link` and `logs` through `-p` are exercised; rendered config asserts the pass-through, `127.0.0.1`, `PUBLIC_URL` following `PORT` and the default image; replacing only the key makes the app refuse to start with the fatal text and its README pointer and no key in the log; removes its volumes and image). CI job `quickstart`.
- Image smoke test: `bash scripts/smoke.sh` (`SMOKE_IMAGE=<image>` runs the app from a prebuilt image, `SMOKE_CLI` is the CLI command inside it, default `mcp-registry`: `SMOKE_IMAGE=mcp-registry:compat bash scripts/smoke.sh`; separate compose project on port 38080 + `scripts/smoke.compose.yml` with a test upstream, Dockerfile target `smoke-go` (the Go programs `compat/cmd/smoke-upstream` and `compat/cmd/smoke-client`, `-tags compat`, Docker-free tests run in `make go-verify`; always rebuilt by the script, never in the runtime image); the CLI creates an admin, a token and a `shared_secret` server, the client runs in the upstream's container (`compose exec -T -e SMOKE_TOKEN upstream smoke-client http://app:3000 smoke.echo`, the token only through the environment; `ALLOWED_HOSTS=app` lets `/mcp` accept that Host) and runs `search_tools -> describe_tool -> call_tool`, checking each answer for the upstream secret before printing it; the upstream logs `request <method> authorized=<bool>` per request and the script checks it got the secret header while the client and the app log never saw it; needs docker, curl and openssl only; removes its volume).
