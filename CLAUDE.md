# mcp-registry: guide for agents and contributors

Self-hosted MCP gateway (TypeScript, DDD modular monolith, Postgres + pgvector, MCP). The agent sees four meta-tools (`list_servers`, `search_tools`, `describe_tool`, `call_tool`), not the upstream tools. User-facing setup is in `README.md`; this file is the single source of rules for code changes (`AGENTS.md` points here).

## Layers inside a module

```
interfaces      -> MCP transport, HTTP routes, zod validation of input
application     -> use cases and queries; declares ports (repositories, UpstreamClient, Embedder, Clock, SecretBox...)
domain          -> aggregates, value objects, events, invariants. Plain TypeScript, no dependencies
infrastructure  -> port implementations: Postgres repositories, upstream MCP client, OIDC, encryption, embedder
```

Rules are enforced automatically by `pnpm arch` (dependency-cruiser) and `pnpm test` (`apps/server/test/architecture.test.ts`: every rule has a failing fixture, plus the schema ownership check). A rule without a failing fixture does not count: add both together.

- `domain-is-pure`: `domain` imports nothing outside its own `domain` and `shared-kernel`. No npm packages, no `node:*`, no I/O.
- `application-only-domain`: `application` imports only its module's `domain`/`application`, `shared-kernel`, the public `index.ts` of other modules, and npm `zod`.
- `no-inward-infra`: `domain` and `application` never import `infrastructure`, `interfaces` or `platform`.
- `npm-only-in-infra` + `npm-only-in-infra-transport`: `openid-client`, `postgres`, `@huggingface/transformers` and `node:crypto` only in `infrastructure` and `platform`, behind ports. The MCP SDK (`@modelcontextprotocol/*`) and its validators (`ajv`, `ajv-formats`, `@cfworker/json-schema`) are also allowed in `interfaces` (transport); `hono` is allowed in `interfaces`. None of these in `domain`, `application`, `shared-kernel` or `apps/web`.
- `modules-via-index`: modules talk only through their public `index.ts` or through domain events via the outbox. Importing another module's internals is forbidden.
- `web-no-server`, `api-no-ui`, `no-circular`, `no-radix`.
- **Schema ownership.** Each module owns its database schema (`identity.*`, `catalog.*`, `connections.*`, `search.*`, `gateway.*`); other modules' tables are never read or written, not even in SQL joins. Cross-cutting tables live in `platform` (outbox, audit, migrations). Checked by `foreignSchemaRefs` (`apps/server/test/architecture/schema-ownership.ts`, parsed with `@swc/core`): SQL in non-test files under `modules/<m>/**` (tagged templates `` sql`...` ``/`` tx`...` ``, `.unsafe(...)` arguments, SQL-looking strings) must not contain `<other module>.<table>`; fixtures `schema-foreign`/`schema-allowed`.
- Business rules live in `domain`, not in use cases: a use case only orchestrates ports and the domain. `platform/` is composition and cross-cutting infrastructure (config, db, outbox, http, mcp, scheduler); no business logic there.

Layout: `apps/server/src/modules/{identity,catalog,connections,search,gateway}/{domain,application,infrastructure,interfaces}` (each module has a public `index.ts`; `search` has no `interfaces`, the gateway calls it), `apps/server/src/shared-kernel` (Result, errors, events, Clock, AuditLog port), `apps/server/src/platform` (composition: `container.ts`, `main.ts`, `config.ts`, `db.ts`, `migrate.ts`, `outbox*.ts`, `http/`, `mcp/`), `apps/web` (SPA), `packages/contracts` (zod schemas of the REST API).

## Design decisions

- **Modular monolith.** One Node.js process (Hono), one repository, five modules with hard, machine-checked boundaries. Simple deployment and in-process transactions; a module can be split out later along existing boundaries. The cost is ceremony (ports, fakes in tests) even for simple cases.
- **Postgres without an ORM.** Postgres + pgvector is the only store; access through the `postgres` client and plain SQL, only in `infrastructure` (and `platform` for cross-cutting tables). Row-to-aggregate mapping is written by hand. Migrations are versioned SQL files in `apps/server/migrations`, applied at startup under an advisory lock. Integration tests run against real Postgres (Testcontainers).
- **Transactional outbox.** Catalog writes domain events to `platform.outbox` in the same transaction as the aggregate change; an in-process worker delivers them (`FOR UPDATE SKIP LOCKED`) to subscribers (Search). At-least-once delivery, so handlers are idempotent; retries with exponential backoff, after 10 attempts a periodic sweep takes over. Errors are stored as a neutral label, never message text (it may quote values). No message broker.
- **Local embeddings.** `transformers.js` with `Xenova/multilingual-e5-small` (384 dims, `passage: `/`query: ` prefixes), baked into the image and checked by SHA-256 (`scripts/download-model.mjs`). An OpenAI-compatible HTTP adapter sits behind the same `Embedder` port. Ranking is Reciprocal Rank Fusion over FTS and vector. Changing the model requires a full reindex and a vector dimension migration.
- **Search threshold.** Without a floor, vector search returns the whole index in some order and never says "nothing matches". A vector candidate passes only if cosine similarity >= `SEARCH_MIN_SIMILARITY` (default 0.83; FTS candidates are not filtered). Score = `rrf / (2 / (k + 1))`, `k = 60`, always in `(0, 1]`, not normalised to the best hit. Access and `hidden` filters are applied in the candidate query so `limit` is not eaten by inaccessible tools. Calibration on real Gitea (61) and YouTrack (23) tool lists: relevant queries scored >= 0.859, unrelated ones <= 0.809, so 0.83 sits in the gap with margin for q8 noise (~0.005). The sample is small; recalibrate for another model or corpus. Embeddings are computed one document per call: the q8 model uses one dynamic activation scale per batch, which shifts vectors by up to ~0.005 depending on batch neighbours.
- **Strict CSP.** `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; frame-ancestors 'none'`, emitted by `securityHeaders()` (`apps/server/src/platform/http/security.ts`) on every response. No inline scripts or styles, no `unsafe-eval`, hashes or nonces. Pinned by `apps/server/test/http/csp.test.ts`, `platform.int.test.ts`, `apps/web/src/app/csp.test.tsx`, `Toaster.test.tsx`, `zod-config.test.ts` and `e2e/csp.spec.ts`.
- **Upstream auth findings** (spike against `gitea-mcp` 1.11 in HTTP mode and YouTrack 2026.2 `/mcp`): both accept a person's OAuth access token per request (different people interleaved in one upstream process each see themselves), via `Authorization: Bearer {secret}`; both accept PATs with the same header; both answer an invalid token with HTTP 401, so `UpstreamClient` maps 401 to `UpstreamError('unauthorized')` with no special cases. Access tokens live 3600 s. Gitea issues a new refresh token on refresh but the old one keeps working unless `[oauth2] INVALIDATE_REFRESH_TOKENS=true`; Hub reuses the same refresh token and issues one only with `access_type=offline`. Gitea needs no scopes; Hub's scope is the YouTrack service ID. `tools/list` does not depend on the user, so syncing the catalog with an admin's token is correct. Single-flight refresh stays (it covers one-time refresh tokens and removes duplicate refreshes). `pat_user` remains as a fallback mode. Recorded `tools/list` fixtures: `apps/server/test/fixtures/tools/{gitea,youtrack}.json`.

## Domain vocabulary

- **Server**: catalog aggregate. `slug` (kebab-case, tool-name prefix), name, description, upstream URL (Streamable HTTP), auth mode (`oauth_user` | `pat_user` | `shared_secret` | `none`), access (all permitted people or a list of groups), call timeout, daily limit per person, status (`active` | `disabled`).
- **Tool**: snapshot of an upstream tool (`tools/list`): name, title, description, `inputSchema`, `outputSchema`, annotations and a `hidden` flag set by an admin that survives sync. A hidden tool is neither searched nor callable.
- **ToolRef**: the agent-facing name `<server>.<tool>`, split at the **first** dot (upstream names may contain dots).
- **AuthMode**: how the gateway authenticates to the upstream: `none`, `shared_secret`, `pat_user`, `oauth_user` (+ `OAuthClientConfig`: authorize/token/revoke URL, client ID, scopes, `extraAuthorizeParams`, e.g. `access_type=offline` for Hub; they cannot override flow parameters such as `state`, `redirect_uri`, `scope`; scope `openid` is rejected since there is no discovery to verify an ID token); `header` and a `template` with `{secret}`. The header is built only by `AuthMode.headerFor` (catalog/domain).
- **Access / canUse**: who may use a server (`all` or groups): admins any active server, nobody a `disabled` one (catalog/domain).
- **SecretBox**: encryption port (shared-kernel); AES-256-GCM implementation in `platform/crypto/secret-box.ts` (with `SECRETS_KEY_OLD` it also opens with the previous key, always seals with the current one). The server secret is stored only sealed in `catalog.servers.secret`; `ServerView` exposes only `secretSet`.
- **Key rotation (re-seal)**: `resealSecret(sealed, { from, to })` (shared-kernel) returns `current` (new key already opens it, so repeats are safe) / `resealed` / `unreadable`. Each module re-seals its own data through its own API: `resealServerSecrets` (catalog; `ServerRepository.replaceSealedSecret`, compare-and-set, no `updated_at` or events) and `resealConnections` (connections; `ConnectionStore.listKeys` + `withLock`; `Connection.replaceSealed` keeps status, expiry and `updatedAt`). Run by CLI `rotate-secrets-key`.
- **Connection**: aggregate of `connections`: a person's credentials for a server, `kind` `oauth` (access + refresh + `expiresAt`) or `pat`; `status` `ready` / `expired` (no row = `needs_connection`, listed as `missing`). Tokens are held only sealed (table `connections.connections`). Domain rules: `credentialPlan` (refresh early when < 60 s to `expiresAt` or on `forceRefresh`; without a refresh token use until expiry; `expired` is not refreshed until reconnect; PATs never refresh), `refreshed` (refresh token from the response, else the previous one), `expire` (ready -> expired), `isRefreshRejected` (expire only on an OAuth error from the token endpoint: `invalid_grant` or HTTP 400/401; timeouts, network errors and other 5xx store nothing; `invalid_client`/`unauthorized_client` with 401 mean the gateway's client credentials are wrong, not the person's: `unavailable`, nothing stored), `usableWhileProviderDown` (provider down but the access token is unexpired and not rejected upstream: use it, else `unavailable`).
- **Server config fingerprint**: `serverFingerprint` (connections/domain): upstream URL, auth kind, authorize/token URL and client ID (not scopes or revoke URL), i.e. everywhere a token or code is sent. Stored on the connection (`issued_for`) and on pending connects. The revoke URL in force at issue time is stored separately (`connections.connections.revoke_url`, `Connection.mayRevokeAt`): `disconnect` revokes only there and only if it equals the current one. If an admin changes fingerprinted fields, the token is never sent to the new place: `resolveCredential` expires the connection (`config_changed`), `disconnect` deletes without revoke, `completeConnect` refuses (`invalid_state`).
- **resolveCredential**: `resolveCredential(deps, { userId, server, forceRefresh? })` -> raw secret (access token or PAT) or `needs_connection` / `expired` (reconnect) / `unavailable` (OAuth provider down, retry later). Refresh is single-flight per (userId, server) in process (`createSingleFlight`) plus `ConnectionStore.withLock` (Pg: `select ... for update` in a transaction) across replicas; the decision is re-made under the lock and another process's fresh token is reused. **Only that row and the provider HTTP request (10 s timeout) happen under `withLock`**: server config and client secret are read before the lock, audit is written after commit (otherwise the transaction waits for a second pool connection and the pool can deadlock). `markExpired` after an upstream 401: immediately for `pat_user`, for `oauth_user` only if a just-refreshed token is rejected too.
- **OAuth connect**: `startConnect` (only `oauth_user` servers the person may use; PKCE S256, `redirect_uri = <PUBLIC_URL>/api/connections/callback`) -> **PendingConnect** (`connections.pending`: one-time `state`, 10 min, owned by the starter, bound to the fingerprint) -> `completeConnect`; `savePat` (only `pat_user`), `disconnect` (deletes and calls revoke if allowed; revoke errors ignored), `listConnections`. Ports in `connections/application/ports.ts`: `OAuthClient` (`OpenidOAuthClient` on `openid-client`, no discovery, HTTP Basic client auth with form-encoded ID and secret per RFC 6749 section 2.3.1; token endpoint errors -> `TokenEndpointError(status, error)`), `ServerDirectory` (over catalog's public API), `ConnectionStore`, `PendingConnects`, `Pkce`. REST: `GET /api/connections`, `POST /api/connections/:server/start` -> `{ url }`, `GET /api/connections/callback` -> 302 to `/connections?connected=<server>` or `?error=<ConnectCallbackError code>`, `PUT /api/connections/:server/pat`, `DELETE /api/connections/:server`. Both browser callbacks (`/api/auth/callback`, `/api/connections/callback`) redirect with `internal` on unexpected errors instead of a JSON 500 (logged without the message). The callback reads the session itself (`sessionPrincipal`) and redirects with `?error=unauthenticated` without one.
- **Callback limitation (SameSite=Strict)**: the session cookie is `SameSite=Strict`, so the browser sends it on the redirect back from an OAuth provider only if provider and gateway are the same site: **https and the same registrable domain** (eTLD+1). A provider on another domain, on `http` with an https gateway, or with a cross-site IdP in the redirect chain yields `?error=unauthenticated`. Supporting those would need a Lax cookie binding the browser to `state`, as identity login does.
- **User / login (identity)**: a person from the OIDC provider (`oidc_sub`), no passwords. `GET /api/auth/login` -> provider (Code + PKCE, state in `identity.oidc_pending`, 10 min, one-time) -> `/api/auth/callback` -> session cookie (12 h idle, 30 days absolute). Members of `OIDC_LOGIN_GROUP` or `OIDC_ADMIN_GROUP` (admins) get in; groups come from the `groups` claim of the ID token, with UserInfo as fallback, and role and groups are refreshed on each login. `returnTo` is a relative path only. Disabling a person revokes all sessions and tokens. `Principal` carries `groups`, `via` and `tokenId` (for `sk_`). Discovery is lazy (`OpenidProvider`): the server starts without the IdP, discovery happens on first login (5 s timeout), is cached after success and retried after failure; while the IdP is down login redirects to `/?loginError=idp_unavailable`, `/mcp` and tokens do not depend on it.
- **ApiToken**: `sk_...` token; only its SHA-256 is stored, with `lastUsedAt`/`revokedAt`. Grants access to `/mcp` only, never to `/api/**`.
- **callTool (gateway)**: `callTool(deps, { principal, ref, arguments })` -> the upstream result **unchanged** (same object) or `isError: true` with a short text (`CALL_TOOL_TEXT` in `gateway/application/call-tool.ts`). Order: tool usable by the person now (`ToolCatalog.toolFor`; hidden, removed, server disabled or closed -> one `not_found`, upstream not called) -> arguments vs `inputSchema` (`ArgsValidator`) -> credentials (before the quota: an unconnected service spends no quota; `unavailable` -> "<Server> is unavailable.", `transport_error`) -> daily limit (`Quota.tryConsume`) -> `UpstreamClient.callTool` with the header from `AuthMode.headerFor`. Upstream 401 (`onUpstreamUnauthorized`, gateway/domain): `oauth_user` one `resolveCredential(forceRefresh)` and one retry (quota not spent twice), second 401 -> `markExpired`; `pat_user` -> `markExpired`, no retry; `shared_secret`/`none` -> rejected text, `transport_error`. `AjvArgsValidator` (MCP SDK's ajv validator; dialect from `$schema`) is advisory, the upstream validates too: `pattern`/`patternProperties` (ReDoS protection, schema positions only) and the top-level `$id` are stripped from a copy before compiling; compiled schemas are cached by SHA-256; an uncompilable schema is not checked (one warn per schema). A failed call-log write never changes the agent's answer; `server`/`tool` in the log are cut to 200 characters.
- **CallOutcome**: `ok`, `upstream_error` (upstream `isError: true` or a JSON-RPC error to `tools/call`, `UpstreamError` kind `rejected`; the agent gets `<Server> rejected the call (JSON-RPC <code>): <upstream message, up to 500 chars>`, never logged), `timeout`, `transport_error` (network, 5xx, `too_large`, rejected server key, OAuth provider down), `denied:not_found` / `invalid_arguments` / `quota` / `needs_connection` / `expired`.
- **QuotaDay**: UTC calendar day `YYYY-MM-DD`, resets at the next UTC midnight. Counter `gateway.quota (user_id, server, day, count)` with an atomic `insert ... on conflict do update ... where count < limit returning`.
- **CallLogEntry**: `gateway.calls`: who, which token (`null` for a session), server, tool, start, duration, `CallOutcome`. No columns for arguments or results. `CallLog.list`: newest first, filters `userId`/`server`/`outcome`/`before`. Kept `CALL_LOG_RETENTION_DAYS`.
- **Search / index**: `search.documents` (ref, server, title, description, body, tsv, embedding), one row per visible tool. Indexed on catalog events `catalog.tools_changed` / `tools_removed` / `server_changed`, data only from catalog's `listToolsForIndex`. Document text `"<server>. <description>\n<name> <title>\n<description>"`. If the embedder fails, the document is stored without a vector (text search works) and `indexMissingEmbeddings` fills it later.
- **searchTools / ToolHit**: `searchTools(deps, { query, limit, servers })` -> `{ ref, server, score }`: FTS + vector through RRF; vector failure is logged as warn and search falls back to text; the `servers` filter applies in SQL before `limit`, empty `servers` -> `[]` without a query. Access is decided by the caller (gateway).
- **Outbox**: event table written in the same transaction as the change; a worker delivers events to subscribers.
- **UpstreamClient**: port to upstream MCP (`shared-kernel/upstream.ts`): `listTools` (all pages), `callTool`; errors are `UpstreamError` kinds `unauthorized` / `timeout` / `too_large` / `transport` / `rejected` (JSON-RPC error; code and text in `rejection`, not `message`). `UpstreamTarget` = URL + ready headers + `timeoutMs` + `maxResponseBytes`. Implementation `platform/upstream/mcp-upstream-client.ts`: a new MCP session per operation, one timeout per operation, response bytes counted as a stream and the operation aborted on overflow, redirects refused; messages never contain response bodies or credentials. Test upstream: `apps/server/test/fake-upstream.ts`.
- **Catalog sync**: `syncServer` (catalog/application): upstream `tools/list` -> `reconcileTools` -> `tools_changed`/`tools_removed`. `principal` is an admin (button) or `null` (scheduler). Credentials: `none` none, `shared_secret` the server secret, `oauth_user`/`pat_user` the personal secret of the sync owner (the admin who pressed sync, or `sync_user_id`, the last successful admin, for the scheduler). Rules in catalog/domain **SyncOwner**: `mayLend` (only while that person is an enabled admin, else `needs_connection`), `failureOf`. Port **SyncCredentials** wired in `platform/upstream/sync-credentials.ts`. On failure tools are unchanged and `last_sync_error` holds `syncFailureText`. **SyncRecord** (`Server.applySync`, `saveSyncState`): `last_sync_at` is the start of the last attempt; an older attempt never overwrites it; only a successful admin sync changes `sync_user_id`.
- **Catalog and admin REST** (session + `Origin`; Bearer -> 401; admin routes 403 for members before parsing the body, `requireAdminRole`). Server edits use optimistic concurrency: `catalog.servers.version`, `PgServerRepository.save` writes only at the read version, else `server_conflict` -> HTTP 409; the secret is written only when the aggregate changed it (`Server.secretChanged`), so a concurrent `rotate-secrets-key` is not rolled back. `GET /api/catalog`; admin: `GET/POST /api/servers` (`POST` = `registerServer`: create + immediate sync; a sync failure does not undo creation), `GET/PUT /api/servers/:slug`, `PUT .../secret`, `POST .../status`, `POST .../sync` -> `{ added, changed, removed }` (`needs_connection` 400, `sync_failed` 502), `GET .../tools`, `PUT .../tools/:name/hidden`, `GET /api/calls`, `GET /api/audit`. Contracts in `packages/contracts/src/{servers,tools,calls,audit}.ts`; `ServerView` passes through its zod schema (extra fields dropped). Body validation errors are 422.
- **MCP interface**: `platform/mcp/` (composition only): `server.ts` (`/mcp`, Streamable HTTP, one `McpServer` per request; body limit `MCP_MAX_BODY_BYTES` in both `bodyLimit` and the SDK's `maxRequestBodySize`, the rest of HTTP 1 MiB; Host -> Origin -> `requireBearerToken` -> handler; `tools.listChanged: false`), `tools.ts` (the four meta-tools; their set and schemas never depend on the catalog; `tools/list` + `instructions` < 8000 characters), `instructions.ts`, `text.ts` (`shortDescription` <= 200 characters, cut at a word). `search_tools` searches only servers the person may use and re-checks each hit with `getToolFor`. Upstream URLs and auth settings are never exposed over MCP. Unexpected errors -> `Internal error.` (logged without arguments).
- **AgentConnection**: what the agent learns about a server's connection: `not_required` (`none`/`shared_secret`), else `ready` / `expired` / `needs_connection`; the latter two get `connectUrl = <PUBLIC_URL>/connections` in `list_servers`.
- **Scheduler**: `platform/scheduler.ts`: `syncAllServers` at start and every `SYNC_INTERVAL_HOURS` (an unexpected error on one server is recorded as `SyncRecord.failure('internal')`, the others continue); `pruneGatewayHistory` (call log older than retention, quota counters older than yesterday UTC) and `pruneExpiredSessions` (identity) at start and daily. Delays longer than the `setTimeout` limit (~24.8 days) are split. A failed run is logged and the schedule continues.

## Operator CLI

`platform/cli.ts` (entry, `dist/cli.js`) -> `platform/cli-commands.ts` (`runCli(argv, container, io)`: argument parsing and use cases through modules' public `index.ts`, no SQL; exit codes 0 / 1 operation failed / 2 bad invocation) and `platform/cli-input.ts` (secret from stdin, no echo on a TTY). Commands: `create-user --sub --name [--admin]` (`provisionUser`, idempotent by `sub`), `create-token <sub> --name`, `create-server --json <file> --as <sub> [--secret-env VAR]` (`ServerInput`, `registerServer`; the secret only from stdin or a variable, never printed), `sync <slug> [--as <sub>]`, `reindex` (`reindexAll`), `rotate-secrets-key` (audit `secrets.rotate`). Test: `apps/server/test/cli.int.test.ts`.

## How to add a use case

1. Domain test first (`*.test.ts` next to the code): aggregate/value object invariants, red -> green. Domain rules go in `domain`, not in the use case.
2. Use case in `application/` with fake ports in its test (no database); declare ports there.
3. Port adapter in `infrastructure/` (Postgres, MCP client, encryption...).
4. Integration test `apps/server/test/**/*.int.test.ts` (Testcontainers, real Postgres).
5. Wire it into `interfaces/` (route / MCP tool) and the composition root `platform/container.ts`.

A new module, term or command updates this file in the same change.

## Web UI (`apps/web`)

React 19 + Vite SPA (via Vite+), served by the same server. UI kit: **shadcn/ui on Base UI**; Radix is forbidden (`no-radix` rule in dependency-cruiser and the `pnpm-lock.yaml` check in `pnpm arch`). Pages: `/catalog`, `/connections`, `/tokens` (everyone) and `/admin/{servers,servers/new,servers/:slug,users,calls,audit}` (admins; members see "no access" and no menu entries). Everything is behind `RequireAuth`: a signed-out visitor sees `LoginPage` at the same URL (a link to `/api/auth/login?returnTo=`; `/?loginError=<code>` is shown as text). `/connections?connected=...|error=...` after the OAuth callback shows a toast / `ErrorAlert` and clears the query string. Server form: `admin/servers/formModel.ts` (state -> request body, zod errors per field, server `invalid_*` errors mapped to fields) and `ServerForm.tsx`; secrets in the form are write-only. Tokens (`sk_`) and secrets are never kept in the query cache or shown after the dialog closes.

- `src/main.tsx`: root with `QueryClientProvider`, router, `<Toaster />`; `src/app/`: shell (`Layout`) and routes.
- `src/api/client.ts`: typed client `api.get/post/put/delete`, responses validated with `@mcp/contracts` schemas, errors as `ApiError` (`src/api/errors.ts`), 401 -> `onUnauthorized` subscribers. `src/api` imports no components.
- `src/components/ui/`: generated by the shadcn CLI and committed, not formatted by `vp fmt`. Add a component from `apps/web`: `pnpm dlx shadcn@4.23.0 add <name>` (`pnpm --filter ... dlx` does not work in pnpm 11). Edit a generated file only with a `// changed: <why>` comment. Base UI components take `render={<Link .../>}`, not `asChild`.
- Own components only where shadcn has none; Tailwind classes and `cn()` from `src/lib/utils.ts`, colours only through theme variables. No CSS files except `src/styles/global.css`.
- All UI strings are English and live in `src/strings.ts`. Success: `notify.success(text)` from `src/lib/notify.ts` (Base UI Toast); form errors under the field. `sonner` is not used: it injects a `<style>`, which the CSP forbids.
- `web` never imports `apps/server` (`web-no-server`): shared types only via `@mcp/contracts`.

CSP: the tree is wrapped in `<CSPProvider disableStyleElements>` (in `main.tsx` and `renderWithApp`), and rules Base UI would inject as `<style>` live statically in `global.css`. Zod runs jitless (`src/zod-config.ts`, imported first in `main.tsx`), since its JIT probe `new Function('')` triggers a `script-src` violation. A new dependency that injects `<style>` breaks `e2e/csp.spec.ts`: configure it (provider, shadow root, static CSS), never weaken the policy with hashes or `'unsafe-inline'`. Mutations are `fetch` with `credentials: 'same-origin'` (the server checks `Origin`; Bearer on `/api/**` is refused).

Adding a page: component in `src/<section>/XxxPage.tsx`, strings in `strings.ts`, data through `api` and TanStack Query, route in `src/app/routes.tsx`, menu item in `Sidebar` (`src/app/Layout.tsx`); its test renders with `renderWithApp(ui, { route, path })` from `test/setup.ts` (QueryClient without retries, memory data router, `<Toaster />`); network through msw (`test/msw/handlers.ts`, `server.use(...)`; an unhandled request fails the test).

Run: `pnpm dev:web` (Vite, proxies `/api` and `/mcp` to `localhost:3000`), `pnpm build:web` -> `apps/web/dist`. Web tests are the `web` project in `vp test` (jsdom).

## Running locally

- Tests: `pnpm install`, then `pnpm verify`. Docker is required: integration tests start Postgres through Testcontainers.
- Server build: `pnpm build` (`vp pack`) produces `apps/server/dist/main.js` and `dist/cli.js`. The server does not run from sources.
- Full box: `cp .env.example .env`, fill in `POSTGRES_PASSWORD`, `SECRETS_KEY` (`openssl rand -base64 32`) and `OIDC_*`, then `docker compose up -d --build`; check `curl localhost:3000/healthz`.
- Image smoke test: `bash scripts/smoke.sh` (separate compose project on port 38080 + `scripts/smoke.compose.yml` with a test upstream, Dockerfile target `smoke-upstream`, `apps/server/test/smoke/upstream.ts`, not in the runtime image; the CLI creates an admin, a token and a `shared_secret` server, `apps/server/test/smoke/mcp-client.ts` runs `search_tools -> describe_tool -> call_tool` and checks the upstream got the secret header while the client and logs never saw it; removes its volume).
