# mcp-registry: guide for agents and contributors

Self-hosted MCP gateway (TypeScript, DDD modular monolith, Postgres + pgvector, MCP). The agent sees four meta-tools (`list_servers`, `search_tools`, `describe_tool`, `call_tool`), not the upstream tools. User-facing setup is in `README.md`; this file is the single source of rules for code changes (`AGENTS.md` points here).

## Layers inside a module

```
interfaces      -> MCP transport, HTTP routes, zod validation of input
application     -> use cases and queries; declares ports (repositories, UpstreamClient, Embedder, Clock, SecretBox...)
domain          -> aggregates, value objects, events, invariants. Plain TypeScript, no dependencies
infrastructure  -> port implementations: Postgres repositories, upstream MCP client, OIDC, encryption, embedder
```

Rules are enforced automatically by `pnpm arch` (dependency-cruiser) and `pnpm test` (`apps/server/test/architecture.test.ts`: every rule has a failing fixture, plus the schema ownership check). A rule without a failing fixture does not count: add both together.

- `domain-is-pure`: `domain` imports nothing outside its own `domain` and `shared-kernel`. No npm packages, no `node:*`, no I/O.
- `application-only-domain`: `application` imports only its module's `domain`/`application`, `shared-kernel`, the public `index.ts` of other modules, and npm `zod`.
- `no-inward-infra`: `domain` and `application` never import `infrastructure`, `interfaces` or `platform`.
- `npm-only-in-infra` + `npm-only-in-infra-transport`: `openid-client`, `postgres`, `@huggingface/transformers` and `node:crypto` only in `infrastructure` and `platform`, behind ports. The MCP SDK (`@modelcontextprotocol/*`) and its validators (`ajv`, `ajv-formats`, `@cfworker/json-schema`) are also allowed in `interfaces` (transport); `hono` is allowed in `interfaces`. None of these in `domain`, `application`, `shared-kernel` or `apps/web`.
- `modules-via-index`: modules talk only through their public `index.ts` or through domain events via the outbox. Importing another module's internals is forbidden.
- `web-no-server`, `api-no-ui`, `no-circular`, `no-radix`.
- **Schema ownership.** Each module owns its database schema (`identity.*`, `catalog.*`, `connections.*`, `search.*`, `gateway.*`); other modules' tables are never read or written, not even in SQL joins. Cross-cutting tables live in `platform` (outbox, audit, migrations). Checked by `foreignSchemaRefs` (`apps/server/test/architecture/schema-ownership.ts`, parsed with `@swc/core`): SQL in non-test files under `modules/<m>/**` (tagged templates `` sql`...` ``/`` tx`...` ``, `.unsafe(...)` arguments, SQL-looking strings) must not contain `<other module>.<table>`; fixtures `schema-foreign`/`schema-allowed`.
- Business rules live in `domain`, not in use cases: a use case only orchestrates ports and the domain. `platform/` is composition and cross-cutting infrastructure (config, db, outbox, http, mcp, scheduler); no business logic there.

Layout: `apps/server/src/modules/{identity,catalog,connections,search,gateway}/{domain,application,infrastructure,interfaces}` (each module has a public `index.ts`; `search` has no `interfaces`, the gateway calls it), `apps/server/src/shared-kernel` (Result, errors, events, Clock, AuditLog port), `apps/server/src/platform` (composition: `container.ts`, `main.ts`, `config.ts`, `db.ts`, `migrate.ts`, `outbox*.ts`, `http/`, `mcp/`), `apps/web` (SPA), `packages/contracts` (zod schemas of the REST API).

## Design decisions

- **Modular monolith.** One Node.js process (Hono), one repository, five modules with hard, machine-checked boundaries. Simple deployment and in-process transactions; a module can be split out later along existing boundaries. The cost is ceremony (ports, fakes in tests) even for simple cases.
- **Postgres without an ORM.** Postgres + pgvector is the only store; access through the `postgres` client and plain SQL, only in `infrastructure` (and `platform` for cross-cutting tables). Row-to-aggregate mapping is written by hand. Migrations are versioned SQL files in `apps/server/migrations`, applied at startup under an advisory lock. Integration tests run against real Postgres (Testcontainers).
- **Transactional outbox.** Catalog writes domain events to `platform.outbox` in the same transaction as the aggregate change; an in-process worker delivers them (`FOR UPDATE SKIP LOCKED`) to subscribers (Search). At-least-once delivery, so handlers are idempotent; retries with exponential backoff, after 10 attempts a periodic sweep takes over. Errors are stored as a neutral label, never message text (it may quote values). No message broker.
- **Local embeddings.** `transformers.js` with `Xenova/multilingual-e5-small` (384 dims, `passage: `/`query: ` prefixes), baked into the image and checked by SHA-256 (`scripts/download-model.mjs`). An OpenAI-compatible HTTP adapter sits behind the same `Embedder` port. Ranking is Reciprocal Rank Fusion over FTS and vector. Changing the model requires a full reindex and a vector dimension migration.
- **Search threshold.** Without a floor, vector search returns the whole index in some order and never says "nothing matches". A vector candidate passes only if cosine similarity >= `SEARCH_MIN_SIMILARITY` (default 0.83; FTS candidates are not filtered). Score = `rrf / (2 / (k + 1))`, `k = 60`, always in `(0, 1]`, not normalised to the best hit. Access and `hidden` filters are applied in the candidate query so `limit` is not eaten by inaccessible tools. Calibration on real Gitea (61) and YouTrack (23) tool lists: relevant queries scored >= 0.859, unrelated ones <= 0.809, so 0.83 sits in the gap with margin for q8 noise (~0.005). The sample is small; recalibrate for another model or corpus. Embeddings are computed one document per call: the q8 model uses one dynamic activation scale per batch, which shifts vectors by up to ~0.005 depending on batch neighbours.
- **Strict CSP.** `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; frame-ancestors 'none'`, emitted by `securityHeaders()` (`apps/server/src/platform/http/security.ts`) on every response. No inline scripts or styles, no `unsafe-eval`, hashes or nonces. Pinned by `apps/server/test/http/csp.test.ts`, `platform.int.test.ts`, `apps/web/src/app/csp.test.tsx`, `Toaster.test.tsx`, `zod-config.test.ts` and `e2e/csp.spec.ts`.
- **Upstream auth findings** (spike against `gitea-mcp` 1.11 in HTTP mode and YouTrack 2026.2 `/mcp`): both accept a person's OAuth access token per request (different people interleaved in one upstream process each see themselves), via `Authorization: Bearer {secret}`; both accept PATs with the same header; both answer an invalid token with HTTP 401, so `UpstreamClient` maps 401 to `UpstreamError('unauthorized')` with no special cases. Access tokens live 3600 s. Gitea issues a new refresh token on refresh but the old one keeps working unless `[oauth2] INVALIDATE_REFRESH_TOKENS=true`; Hub reuses the same refresh token and issues one only with `access_type=offline`. Gitea needs no scopes; Hub's scope is the YouTrack service ID. `tools/list` does not depend on the user, so syncing the catalog with an admin's token is correct. Single-flight refresh stays (it covers one-time refresh tokens and removes duplicate refreshes). `pat_user` remains as a fallback mode. Recorded `tools/list` fixtures: `apps/server/test/fixtures/tools/{gitea,youtrack}.json`, copied to `compat/fixtures/tools/` (read by the compat fakes, the Go tests and the generators; `TestToolFixtureCopiesEqualTheOriginals` keeps the copies byte-equal while the originals exist).

## Domain vocabulary

- **Server**: catalog aggregate. `slug` (kebab-case, tool-name prefix), name, description, upstream URL (Streamable HTTP), auth mode (`oauth_user` | `pat_user` | `shared_secret` | `none`), access (all permitted people or a list of groups), call timeout, daily limit per person, status (`active` | `disabled`).
- **Tool**: snapshot of an upstream tool (`tools/list`): name, title, description, `inputSchema`, `outputSchema`, annotations and a `hidden` flag set by an admin that survives sync. A hidden tool is neither searched nor callable.
- **ToolRef**: the agent-facing name `<server>.<tool>`, split at the **first** dot (upstream names may contain dots).
- **AuthMode**: how the gateway authenticates to the upstream: `none`, `shared_secret`, `pat_user`, `oauth_user` (+ `OAuthClientConfig`: authorize/token/revoke URL, client ID, scopes, `extraAuthorizeParams`, e.g. `access_type=offline` for Hub; they cannot override flow parameters such as `state`, `redirect_uri`, `scope`; scope `openid` is rejected since there is no discovery to verify an ID token); `header` and a `template` with `{secret}`. The header is built only by `AuthMode.headerFor` (catalog/domain).
- **Access / canUse**: who may use a server (`all` or groups): admins any active server, nobody a `disabled` one (catalog/domain).
- **SecretBox**: encryption port (shared-kernel); AES-256-GCM implementation in `platform/crypto/secret-box.ts` (with `SECRETS_KEY_OLD` it also opens with the previous key, always seals with the current one). The server secret is stored only sealed in `catalog.servers.secret`; `ServerView` exposes only `secretSet`. **Secret reset** (`Server.update`, domain `secretDestinationChanged`): the stored secret is cleared (`secretCleared`, audit `server.secret_clear`) when the place it is sent to changes: auth kind, for `shared_secret` the upstream `url`, for `oauth_user` (the secret is the client secret) `tokenUrl`, `revokeUrl` or `clientId`; header, template, scopes, authorize URL and an `oauth_user` upstream URL keep it. `PUT /api/servers/:slug` takes no secret; the form sends `PUT .../secret` after it, so a secret entered in the same save is kept (`secretResetReason` in `formModel.ts` only mirrors the rule for the warning before saving, and the form says afterwards that the secret must be entered again). **`SECRETS_KEY_FILE` / `PGPASSWORD_FILE`** (`platform/config.ts`, `fromFile`): the value is read from the named file and trimmed (for Docker secrets and the quick start); a variable together with its `_FILE` twin is a startup error, an unreadable or empty file too; errors name the variable and the path, never the content. `PGPASSWORD_FILE` becomes `Config.databasePassword`, which `platform/db.ts` passes to the client over the URL and `PGPASSWORD`.
- **Key check** (`platform/crypto/key-check.ts`, all its SQL): `platform.key_check` (migration `0010_key_check.sql`, one row) holds a known text sealed with the key configured on the first start that has the check. `verifySecretsKey` (verdict by the pure `judgeKeyCheck`) runs at start after migrations and before `announceFirstStart` (`checkSecretsKey` in `platform/bootstrap.ts`) and returns `created` / `ok` / `needs_rotation` / `mismatch`: absent -> created (also the first start after upgrading from 0.1.0); opens with `SECRETS_KEY` -> continue; opens only with `SECRETS_KEY_OLD` -> continue with a warning to run `rotate-secrets-key`; opens with neither -> one `fatal` record (never key material, with a pointer to the README section "Recovering from a key mismatch") and exit code 1. It proves the key is the recorded one, not that it opens the stored secrets, and it is an operational guard, not a security boundary. The server never generates or replaces the key itself. `inspectKeyCheck` is the read-only judgement (the CLI never creates the check); `removeKeyCheck` backs `reset-key-check`.
- **Key rotation (re-seal)**: `resealSecret(sealed, { from, to })` (shared-kernel) returns `current` (new key already opens it, so repeats are safe) / `resealed` / `unreadable`. Each module re-seals its own data through its own API: `resealServerSecrets` (catalog; `ServerRepository.replaceSealedSecret`, compare-and-set retried, 3 attempts in all, exhausted counts as `failed`; no `updated_at` or events) and `resealConnections` (connections; `ConnectionStore.listKeys` + `withLock`; `Connection.replaceSealed` keeps status, expiry and `updatedAt`). The check value is re-sealed by `resealKeyCheck` (platform; compare-and-set, `current` / `resealed` / `unreadable` / `absent`; a lost compare-and-set yields `current`): the CLI prints `key check: re-sealed` / `already current` / `none stored` / `cannot be read with either key`, records it in the audit and exits 1 when anything cannot be opened with either key (a server secret, a connection or the check) or a server secret's compare-and-set ran out of attempts, listing it under `error: neither key opens (left as they were):`. Run by CLI `rotate-secrets-key`.
- **Connection**: aggregate of `connections`: a person's credentials for a server, `kind` `oauth` (access + refresh + `expiresAt`) or `pat`; `status` `ready` / `expired` (no row = `needs_connection`, listed as `missing`). Tokens are held only sealed (table `connections.connections`). Domain rules: `credentialPlan` (refresh early when < 60 s to `expiresAt` or on `forceRefresh`; without a refresh token use until expiry; `expired` is not refreshed until reconnect; PATs never refresh), `refreshed` (refresh token from the response, else the previous one), `expire` (ready -> expired), `isRefreshRejected` (expire only on an OAuth error from the token endpoint: `invalid_grant` or HTTP 400/401; timeouts, network errors and other 5xx store nothing; `invalid_client`/`unauthorized_client` with 401 mean the gateway's client credentials are wrong, not the person's: `unavailable`, nothing stored), `usableWhileProviderDown` (provider down but the access token is unexpired and not rejected upstream: use it, else `unavailable`).
- **Server config fingerprint**: `serverFingerprint` (connections/domain): upstream URL, auth kind, authorize/token URL and client ID (not scopes or revoke URL), i.e. everywhere a token or code is sent. Stored on the connection (`issued_for`) and on pending connects. The revoke URL in force at issue time is stored separately (`connections.connections.revoke_url`, `Connection.mayRevokeAt`): `disconnect` revokes only there and only if it equals the current one. If an admin changes fingerprinted fields, the token is never sent to the new place: `resolveCredential` expires the connection (`config_changed`), `disconnect` deletes without revoke, `completeConnect` refuses (`invalid_state`).
- **resolveCredential**: `resolveCredential(deps, { userId, server, forceRefresh? })` -> raw secret (access token or PAT) or `needs_connection` / `expired` (reconnect) / `unavailable` (OAuth provider down, retry later). Refresh is single-flight per (userId, server) in process (`createSingleFlight`) plus `ConnectionStore.withLock` (Pg: `select ... for update` in a transaction) across replicas; the decision is re-made under the lock and another process's fresh token is reused. **Only that row and the provider HTTP request (10 s timeout) happen under `withLock`**: server config and client secret are read before the lock, audit is written after commit (otherwise the transaction waits for a second pool connection and the pool can deadlock). `markExpired` after an upstream 401: immediately for `pat_user`, for `oauth_user` only if a just-refreshed token is rejected too.
- **OAuth connect**: `startConnect` (only `oauth_user` servers the person may use; PKCE S256, `redirect_uri = <PUBLIC_URL>/api/connections/callback`) -> **PendingConnect** (`connections.pending`: one-time `state`, 10 min, owned by the starter, bound to the fingerprint) -> `completeConnect`; `savePat` (only `pat_user`), `disconnect` (deletes and calls revoke if allowed; revoke errors ignored), `listConnections`. Ports in `connections/application/ports.ts`: `OAuthClient` (`OpenidOAuthClient` on `openid-client`, no discovery, HTTP Basic client auth with form-encoded ID and secret per RFC 6749 section 2.3.1; token endpoint errors -> `TokenEndpointError(status, error)`), `ServerDirectory` (over catalog's public API), `ConnectionStore`, `PendingConnects`, `Pkce`. REST: `GET /api/connections`, `POST /api/connections/:server/start` -> `{ url }`, `GET /api/connections/callback` -> 302 to `/connections?connected=<server>` or `?error=<ConnectCallbackError code>`, `PUT /api/connections/:server/pat`, `DELETE /api/connections/:server`. Both browser callbacks (`/api/auth/callback`, `/api/connections/callback`) redirect with `internal` on unexpected errors instead of a JSON 500 (logged without the message). The callback reads the session itself (`sessionPrincipal`) and redirects with `?error=unauthenticated` without one.
- **Callback limitation (SameSite=Strict)**: the session cookie is `SameSite=Strict`, so the browser sends it on the redirect back from an OAuth provider only if provider and gateway are the same site: **https and the same registrable domain** (eTLD+1). A provider on another domain, on `http` with an https gateway, or with a cross-site IdP in the redirect chain yields `?error=unauthenticated`. Supporting those would need a Lax cookie binding the browser to `state`, as identity login does.
- **User / login (identity)**: a person from the OIDC provider (`oidc_sub`), no passwords. OIDC is optional: `OIDC_ISSUER`, `OIDC_CLIENT_ID` and `OIDC_CLIENT_SECRET` are all set or all unset (a partial set is a startup error naming the missing ones; an empty value counts as unset); without them people sign in with a **LoginLink**, `GET /api/auth/login` redirects to `/?loginError=oidc_not_configured`, and `/mcp` and `sk_` tokens never depend on OIDC. `GET /api/auth/login` -> provider (Code + PKCE, state in `identity.oidc_pending`, 10 min, one-time) -> `/api/auth/callback` -> session cookie (12 h idle, 30 days absolute). Members of `OIDC_LOGIN_GROUP` or `OIDC_ADMIN_GROUP` (admins) get in; groups come from the `OIDC_GROUPS_CLAIM` claim (default `groups`; a list of names, or an object whose keys are the names, as Zitadel's roles) of the ID token, with UserInfo as fallback; the request asks for `OIDC_SCOPES` (default `openid profile email groups`, must include `openid`), and role and groups are refreshed on each login. `returnTo` is a relative path only. Anonymous load is bounded: a failed code exchange is counted per client IP (`callbackLimiter`, an `InMemoryRateLimiter`, `FAILED_CALLBACK_AUDIT_LIMIT` 20 per `FAILED_CALLBACK_WINDOW_SEC` 60, domain `login-flow.ts`) and past the limit `auth.login_failed` is not written, but the exchange is still attempted and a valid code always signs in; starting a login is never limited. `identity.oidc_pending` drops expired rows (`expires_at <= now()`, index `oidc_pending_expires_idx`) on every insert and never evicts an unexpired one (a cap would let an anonymous caller cancel other people's logins): the table is bounded by the start rate times ten minutes, not by a cap; bounding it for real needs the pending state in a signed cookie. Disabling a person deletes all their sessions and pending login links and revokes all their tokens (`setDisabled`). `Principal` carries `groups`, `via` and `tokenId` (for `sk_`). Discovery is lazy (`OpenidProvider`): the server starts without the IdP, discovery happens on first login (5 s timeout), is cached after success and retried after failure; while the IdP is down login redirects to `/?loginError=idp_unavailable`, `/mcp` and tokens do not depend on it.
- **LoginLink**: a one-time sign-in code for one person, for installs without OIDC (and as break-glass access with it). `ll_` + 32 random bytes base64url, valid 15 minutes (`loginLinkExpiry`), only its SHA-256 is stored (`identity.login_links`, `PgLoginLinkRepository`) and the row is removed when used. A person has at most one live link: `issueLoginLink` (identity/application; existing enabled person only, audit `auth.link_issued`) deletes the earlier one; disabling a person removes their links; expired ones are pruned with expired sessions (`pruneExpiredSessions`, scheduler). Link format `<PUBLIC_URL>/login#link=<code>` (`loginLinkUrl`): the code is in the fragment, which browsers do not send to the server. The SPA (`LinkLogin`) handles the fragment only on `/login`, strips it from the URL and sends `POST /api/auth/link` (`completeLinkLogin`): 204 + session cookie, or `invalid_link` 401 (unknown, expired and used are indistinguishable), `disabled` 403, `rate_limited` 429 with `Retry-After`; failed attempts are counted per client IP (fixed window of 60 s, in memory: the 11th failure locks that IP for 60 s and is answered `rate_limited` with `Retry-After`; a valid code is still accepted from a locked-out IP; failed `sk_` checks on `/mcp` have their own limiter, 30 per minute, and the failed-callback audit limiter allows 20 audited records per minute per IP). The SPA never sends a code without one explicit click, whatever the session state (no auto-send: closes login CSRF and the two-tab race): the card names the current account when signed in, and a rejected link whose session check then finds a session (another tab) lands in the app silently. A successful `POST /api/auth/link` that carried a session cookie ends that old session (`logout`) before the new cookie is set; a rejected link leaves it alone. The audit record of a refused consumed link names the person (`actorId`) unless they no longer exist. `GET /api/auth/methods` -> `{ oidc: boolean }` (public); without OIDC the sign-in page shows the `login-link` command instead of the SSO button. Audit: `auth.login` with `via: 'link'`; `auth.login_failed` only when a real link was consumed and then refused (unknown or malformed codes are not audited); the code is never written to audit or errors. A session from a link is an ordinary session; role and groups come from the stored person, and a link sign-in updates only `last_login_at`. Without OIDC there are no groups beyond what `create-user` assigns (login group or admin group): admins see every active server, members see servers open to `all` or to the login group. **First start without OIDC**: `bootstrapLocalAdmin` (identity/application) creates the admin `local-admin` when there are no people and issues a link (`needsBootstrapLink` in identity/domain decides `create` / `reissue` / `none`; two replicas on an empty database both provision, the first one's logged link may be dead, recovery is `login-link local-admin`); `announceFirstStart` (`platform/bootstrap.ts`) logs one `warn` record whose `url` field is the link. It logs a new link on every start (each invalidates the previous) until `local-admin` has signed in once, and never when OIDC is configured or any other person exists; a failure is logged as an error and does not stop the server.
- **ApiToken**: `sk_...` token; only its SHA-256 is stored, with `lastUsedAt`/`revokedAt`. Grants access to `/mcp` only, never to `/api/**`.
- **callTool (gateway)**: `callTool(deps, { principal, ref, arguments })` -> the upstream result as `UpstreamClient.callTool` projects it (`platform/upstream/mcp-upstream-client.ts`: `content`, `structuredContent` only when a plain object and `isError` only when defined; `_meta` and every other field are dropped there, not in `callTool`), or `isError: true` with a short text (`CALL_TOOL_TEXT` in `gateway/application/call-tool.ts`). Order: tool usable by the person now (`ToolCatalog.toolFor`; hidden, removed, server disabled or closed -> one `not_found`, upstream not called) -> arguments vs `inputSchema` (`ArgsValidator`) -> credentials (before the quota: an unconnected service spends no quota; `unavailable` -> "<Server> is unavailable.", `transport_error`) -> daily limit (`Quota.tryConsume`) -> `UpstreamClient.callTool` with the header from `AuthMode.headerFor`. Upstream 401 (`onUpstreamUnauthorized`, gateway/domain): `oauth_user` one `resolveCredential(forceRefresh)` and one retry (quota not spent twice), second 401 -> `markExpired`; `pat_user` -> `markExpired`, no retry; `shared_secret`/`none` -> rejected text, `transport_error`. `AjvArgsValidator` (MCP SDK's ajv validator; dialect from `$schema`) is advisory, the upstream validates too: `pattern`/`patternProperties` (ReDoS protection, schema positions only) and the top-level `$id` are stripped from a copy before compiling; compiled schemas are cached by SHA-256; an uncompilable schema is not checked (one warn per schema). A failed call-log write never changes the agent's answer; `server`/`tool` in the log are cut to 200 characters.
- **CallOutcome**: `ok`, `upstream_error` (upstream `isError: true` or a JSON-RPC error to `tools/call`, `UpstreamError` kind `rejected`; the agent gets `<Server> rejected the call (JSON-RPC <code>): <upstream message, up to 500 chars>`, never logged), `timeout`, `transport_error` (network, 5xx, `too_large`, rejected server key, OAuth provider down), `denied:not_found` / `invalid_arguments` / `quota` / `needs_connection` / `expired`.
- **QuotaDay**: UTC calendar day `YYYY-MM-DD`, resets at the next UTC midnight. Counter `gateway.quota (user_id, server, day, count)` with an atomic `insert ... on conflict do update ... where count < limit returning`.
- **CallLogEntry**: `gateway.calls`: who, which token (`null` for a session), server, tool, start, duration, `CallOutcome`. No columns for arguments or results. `CallLog.list`: newest first (start time, then numeric id), filters `userId`/`server`/`outcome` and the cursor `before` (strictly older) or the pair `before` + `beforeId` (`(started_at, id) < (before, beforeId)`, no skipped ties; the web page sends both; `calls_started_at_idx` serves the range, no migration). Kept `CALL_LOG_RETENTION_DAYS`.
- **Search / index**: `search.documents` (ref, server, title, description, body, tsv, embedding), one row per visible tool. Indexed on catalog events `catalog.tools_changed` / `tools_removed` / `server_changed`, data only from catalog's `listToolsForIndex`. Document text `"<server>. <description>\n<name> <title>\n<description>"`. If the embedder fails, the document is stored without a vector (text search works) and `indexMissingEmbeddings` fills it later.
- **searchTools / ToolHit**: `searchTools(deps, { query, limit, servers })` -> `{ ref, server, score }`: FTS + vector through RRF; vector failure is logged as warn and search falls back to text; the `servers` filter applies in SQL before `limit`, empty `servers` -> `[]` without a query. Access is decided by the caller (gateway).
- **Outbox**: event table written in the same transaction as the change; a worker delivers events to subscribers.
- **UpstreamClient**: port to upstream MCP (`shared-kernel/upstream.ts`): `listTools` (all pages), `callTool`; errors are `UpstreamError` kinds `unauthorized` / `timeout` / `too_large` / `transport` / `rejected` (JSON-RPC error; code and text in `rejection`, not `message`). `UpstreamTarget` = URL + ready headers + `timeoutMs` + `maxResponseBytes`. Implementation `platform/upstream/mcp-upstream-client.ts`: a new MCP session per operation, one timeout per operation, response bytes counted as a stream and the operation aborted on overflow, redirects refused; messages never contain response bodies or credentials. Test upstream: `apps/server/test/fake-upstream.ts`.
- **Catalog sync**: `syncServer` (catalog/application): upstream `tools/list` -> `reconcileTools` -> `tools_changed`/`tools_removed`. `principal` is an admin (button) or `null` (scheduler). Credentials: `none` none, `shared_secret` the server secret, `oauth_user`/`pat_user` the personal secret of the sync owner (the admin who pressed sync, or `sync_user_id`, the last successful admin, for the scheduler). Rules in catalog/domain **SyncOwner**: `mayLend` (only while that person is an enabled admin, else `needs_connection`), `failureOf`. Port **SyncCredentials** wired in `platform/upstream/sync-credentials.ts`. On failure tools are unchanged and `last_sync_error` holds `syncFailureText`. **SyncRecord** (`Server.applySync`, `saveSyncState`): `last_sync_at` is the start of the last attempt; an older attempt never overwrites it; only a successful admin sync changes `sync_user_id`.
- **Catalog and admin REST** (session + `Origin`; Bearer -> 401; admin routes 403 for members before parsing the body, `requireAdminRole`). Server edits use optimistic concurrency: `catalog.servers.version`, `PgServerRepository.save` writes only at the read version, else `server_conflict` -> HTTP 409; the secret is written only when the aggregate changed it (`Server.secretChanged`), so a concurrent `rotate-secrets-key` is not rolled back. `GET /api/catalog`; admin: `GET/POST /api/servers` (`POST` = `registerServer`: create + immediate sync; a sync failure does not undo creation), `GET/PUT /api/servers/:slug`, `PUT .../secret`, `POST .../status`, `POST .../sync` -> `{ added, changed, removed }` (`needs_connection` 400, `sync_failed` 502), `GET .../tools`, `PUT .../tools/:name/hidden`, `GET /api/calls`, `GET /api/audit` (newest first by the numeric id, `before` pages by it). Contracts in `packages/contracts/src/{servers,tools,calls,audit}.ts`; `ServerView` passes through its zod schema (extra fields dropped). Body validation errors are 422.
- **MCP interface**: `platform/mcp/` (composition only): `server.ts` (`/mcp`, Streamable HTTP, one `McpServer` per request; body limit `MCP_MAX_BODY_BYTES` in both `bodyLimit` and the SDK's `maxRequestBodySize`, the rest of HTTP 1 MiB; body limit -> Host -> Origin -> `requireBearerToken` -> handler (the limit is the first middleware); `tools.listChanged: false`), `tools.ts` (the four meta-tools; their set and schemas never depend on the catalog; `tools/list` + `instructions` < 8000 characters), `instructions.ts`, `text.ts` (`shortDescription` <= 200 characters, cut at a word). `search_tools` searches only servers the person may use and re-checks each hit with `getToolFor`. Upstream URLs and auth settings are never exposed over MCP. Unexpected errors -> `Internal error.` (logged without arguments).
- **AgentConnection**: what the agent learns about a server's connection: `not_required` (`none`/`shared_secret`), else `ready` / `expired` / `needs_connection`; the latter two get `connectUrl = <PUBLIC_URL>/connections` in `list_servers`.
- **Scheduler**: `platform/scheduler.ts`: `syncAllServers` at start and every `SYNC_INTERVAL_HOURS` (an unexpected error on one server is recorded as `SyncRecord.failure('internal')`, the others continue); `pruneGatewayHistory` (call log older than retention, quota counters older than yesterday UTC) and `pruneExpiredSessions` (identity: expired sessions and expired login links) at start and daily. Delays longer than the `setTimeout` limit (~24.8 days) are split. A failed run is logged and the schedule continues.

## How to add a use case

1. Domain test first (`*.test.ts` next to the code): aggregate/value object invariants, red -> green. Domain rules go in `domain`, not in the use case.
2. Use case in `application/` with fake ports in its test (no database); declare ports there.
3. Port adapter in `infrastructure/` (Postgres, MCP client, encryption...).
4. Integration test `apps/server/test/**/*.int.test.ts` (Testcontainers, real Postgres).
5. Wire it into `interfaces/` (route / MCP tool) and the composition root `platform/container.ts`.

A new module, term or command updates this file in the same change.

- **Secret-carrying types** (`internal/kernel/secret.go`). A plaintext secret, token, code, key or ciphertext held in a struct field (people's tokens and PATs, server and OAuth client secrets, session ids, `sk_` tokens, `ll_` codes, OIDC/OAuth state, code, verifier and nonce, sealed bytes) is a `kernel.Secret` (string) or `kernel.SecretBytes` ([]byte), never a `string`/`*string`/`[]byte`: both keep the value two unexported pointers deep, so fmt (any verb, any holding, an unexported field of another struct included), slog and JSON print `[Redacted]` (`[unset]` for the zero value, which means "not set"; `kernel.NewSecret("")` is a set empty secret, `config.NewSecret("")` is unset), and they are not comparable (`==` is a compile error; the gateway compares through the constant-time `SecretComparer`). The value is read only by `Reveal()`, at the boundary that sends, seals, hashes or stores it; wire formats that must carry it (the created token's response, a decoded request body) use a named DTO filled by `Reveal`, never a marshalling secret type, and SQL arguments and scan targets are plain values (a Secret passed where `any` is accepted compiles but never carries the value: pgx stores the marker and fmt prints it, silently; the check is `internal/archtest` `SecretsIntoEmptyInterfaces`, `TestRepositoryPassesNoSecretToAnEmptyInterface`, which type-checks the non-test code of `internal/` and `cmd/` under the default and `integration` tags (golang.org/x/tools/go/packages; `onnx` is not covered: its cgo files need the native libraries) and fails on any expression whose type is or holds `kernel.Secret`/`SecretBytes` converted to an interface with no methods (fmt, slog, pgx, json, `[]any`, `map[string]any`, `any` returns and assignments, multi-value calls `a, b = f()`, function values whose parameters or results hold a secret, and arguments bound to a type parameter whose constraint has no methods, unless the generic function is declared in the same package and its body never lets a value of its type parameters reach an empty interface; generated files are scanned too); interfaces with methods (ports) stay legal; fixtures `secret-into-any` and `secret-into-any-allowed`, registered with the other Go-coded rules in `TestEveryGoRuleHasAFailingFixture`). `config.Secret`/`SecretBytes` are aliases of the kernel types and `crypto.Keys` holds two `kernel.SecretBytes`. `kernel/secrettest` (`AssertUnprintable`) checks a value in 15 holdings x 12 verbs, slog text and JSON and `json.Marshal`; each package that holds secrets has a `TestSecretCarryingTypesAreUnprintableHoweverHeld`. The connections and search scenarios were split mechanically into subtests per surface, with the same requests and assertions, so the skip list could be exact; `connNewPerson` still opens a person's MCP session lazily). `TestPlatformStartsOnReferenceDatabase` and `TestPlatformReverseHandOver` also hand over people, sessions and an API token between the images (old session cookies and the token row accepted, a new sign-in works; the token on `/mcp` is judged by `TestUpgradeKeepsEverything`), connections (an `oauth_user` server with the administrator's and a member's OAuth connection and a `pat_user` server with two personal tokens: still `ready` after the swap, rows byte for byte, a sync sends the stored tokens, an expiring access token is refreshed once with the STORED refresh token, a disconnect revokes at the stored revoke URL: the cross-image proof that `issued_for` compares equal) and a catalog server (a `shared_secret` server with tools, one hidden, created on one image is read and synchronised on the other with the stored secret, in both directions). Both are set with `:=`, so an environment variable does not override them: pass them on the make command line (`make compat-go COMPAT_GO_SKIP=`; `$$` is a literal `$`). Before running, `make compat-go` lists the pattern (`go test -list`, nothing starts) and fails unless it matches exactly as many scenarios as `COMPAT_GO_TESTS` names, so a renamed scenario cannot pass by running nothing; it also refuses to start without `mcp-registry:compat-ts` (the reference: the scenarios compare with it or start from it). CI job `compat-go` (arm64 and amd64, each runner builds the reference image and the Go image natively and runs `make go-test-onnx-parity` first; after `go`, not required). `make compat-image-go` fails when the version read from `apps/server/package.json` is empty and, after the build, when `docker run --rm mcp-registry:compat-go mcp-registry --version` is not that version. The Go image has no `HEALTHCHECK` yet (the TypeScript one runs node); it needs one before it replaces the published image. `make e2e-flows-go` (CI job `e2e-flows-go`, arm64, not required) runs against the Go image all twelve flows (`E2E_GO_SPECS` in the `Makefile`: `00` to `12`, `03-tokens` and `09-permissions` since milestone 6, which use `/mcp` and the call log); `TestControlOperationsAgainstARealStack` (it uses `/mcp`) runs in `make e2e-flows` against the reference image. `Stack.Answers` (the liveness probe after a start or swap) asks `GET /` with `Accept: text/html`, status 200 only, because the UI shell belongs to the platform layer and `/api/auth/methods` to identity; the self-check proxy changes the status of no response on `/`. `TestPlatformStartsOnReferenceDatabase` (`compat/platform_reference_db_test.go`): a stack on the reference image, then `SwapImage` to the image under test with the same key: healthy, the same migration names (none applied; the count is what the first stack recorded), the key check unchanged, the shell served, no record at error level or above; another key and an unknown migration row are refused with exit 1 and one fatal record (the key-mismatch text; the two operator-facing fragments of the newer-database message). `TestPlatformReverseHandOver` (same file) is the rollback: a stack on the image under test creates the schema and the key check, then `SwapImage` to the reference image with the same key: healthy, nothing applied, the key check byte for byte, the shell served. On the reference image both are restart tests. `TestPlatformWithoutPeople` (`compat/platform_anonymous_test.go`): everything observable without a person, a session, a token or the CLI: the seven security headers and `X-Request-Id` on every kind of answer, the origin check before routing, the oversized body refused before both (declared length and chunked), the access record (path without query, no credentials), the forwarded address with and without `TRUST_PROXY`, and a stack configured through `SECRETS_KEY_FILE` and `PGPASSWORD_FILE`. The reference image sometimes ends with exit code 137 when it is stopped within seconds of first answering healthy (cause not established); later stops exit 0. Hence there is no stop scenario.

- **Suite self-check** (`make compat-selfcheck`, tag `selfcheck`, `compat/selfcheck/`, about 4-5 minutes): builds `mcp-registry:compat-broken` from the reference image (the published 1.0.1, `SELFCHECK_BASE` overrides it; the target pulls it first). `entrypoint.sh` runs the app alone when `BREAK` is unset; with `BREAK` set it starts the app on another port and a dependency-free Node proxy (`proxy.mjs`) on the public one, and the container ends as soon as either child does (a dead proxy exits 1; otherwise the app's exit code). The proxy applies one distortion: `csp`, `origin`, `extra-field`, `status`, `mcp-desc`, `www-auth`, `audit-drop`, `token-in-list` (`passthrough` = no distortion). `selfcheck_test.go`: two controls that must pass (no proxy, which only shows the derived image works and is not a control for the distortion runs; `passthrough`, which skips only the 10 MiB body-limit subtest, because the proxy mishandles that early refusal in a minority of runs, cause not fixed, see `proxy.mjs`), each requiring `--- PASS` for every named subtest; then per distortion one run in which the named subtests must print `--- FAIL`, the output must match a reason pattern only that distortion produces, a canary (`TestPlatformHealthz`) must pass in the same run and the stack must have booted. A distortion that no scenario catches is a gap in the suite: fix the suite, not the self-check. Workflow `compat-selfcheck.yml`: daily and manual, arm64. A new distortion is a new entry in `proxy.mjs` and in `selfcheck_test.go`.
- **Browser flows** (`make e2e-flows`, build tags `compat e2e`, `compat/e2e/` and `e2e/flows/`; about a minute after the image is built; `make compat` does not run it): the real web UI in Chromium against the real application image `COMPAT_IMAGE` (default `mcp-registry:compat-ts`), so the same twelve flows judge the Go server (since milestone 6 all of them) (first start link, OIDC return, token shown once, server form and its errors, hiding a tool, edit conflict, OAuth connect, permissions, disabling a person, session expiry, deep links; `e2e/csp.spec.ts` stays the CSP check). `TestBrowserFlows` boots three stacks (no OIDC; with the fake IdP; one whose public address is `http://gateway.compat.test:<port>` with its OAuth provider at `idp.compat.test`, the same site, which the connect flow needs because the session cookie is `SameSite=Strict`) and the fakes, starts the control API and runs `pnpm exec playwright test -c e2e/flows/playwright.config.ts` (own config, Chromium only, one worker, no retries; the existing `e2e/playwright.config.ts` ignores `flows/`). Chromium maps `host.docker.internal` and `*.compat.test` to 127.0.0.1 through `--host-resolver-rules` (`E2E_HOST_RESOLVER_RULES`). Both fake OAuth providers show a consent page (`fakes.WithConsentPage`): a provider that redirects at once leaves the gateway as the navigation's initiator and hides the `SameSite=Strict` difference, so `08-connect` (same site, connects) and `08b-connect-cross-site` (other site, `?error=unauthenticated`) only differ with the click. **Control API** (`compat/e2e/control.go`, client `e2e/flows/control.ts`): bound to 127.0.0.1 on a random port, every request needs the run's random bearer token (otherwise 401, unit-tested), and it knows only fixed operations with typed parameters, validated and refused on unknown fields: `GET /stacks`, `POST /cli/create-user`, `/cli/login-link`, `/stack/first-start-link`, `/idp/next-login`, `/servers` (registers a server of a given auth kind on a new fake upstream through the admin REST API), `GET /upstream/calls`, `POST /sessions/expire` (a fixed `update identity.sessions set last_seen_at ...`: like the compat suite's time travel it assumes the server under test keeps that schema, which the migration plan requires) and `GET /audit` (read-only, parameterised, filters by actor sub and action, an error rather than a silent cut past 500 rows; since 1.0.1 the image's audit list is ordered newest first by the numeric id, but flows still read specific records here, by actor and action) and `POST /echo` (returns the posted text, for the guard's self-test). No free-form SQL or CLI arguments. The control API's own tests (`TestControl*`) run in `make e2e-flows`; the Docker-free `TestControlRefuses*` and `TestControlEcho*` (token refusal, parameter checks) and `TestPlaywrightArgs*` also run in `make go-verify`. `make e2e-flows` fails when Playwright ran no test; `E2E_PLAYWRIGHT_ARGS` (a spec file) selects flows, `--list`, `--pass-with-no-tests`, `--retries*`, `--grep-invert*`, `--shard*`, `--last-failed`, `--only-changed*`, `-c` in any form (`-c path`, `-cpath`, `-c=path`), `--config*` and `--reporter*` are refused. Every spec runs under the shared fixture (`e2e/flows/fixtures.ts`): no `console.error`, page error or CSP violation (Chromium's own "Failed to load resource ... 401" lines are excused only per named status, path and, where given, page, `guard.excuseRefusal`), no sign-in link code or API token in a response URL, header (the raw ones too, with Set-Cookie) or body (every response the browser received is scanned, or listed as not scanned with a reason, or fails the test: `e2e/flows/guard.ts` holds the state machine. The guard owns page creation, so the capture (a DevTools session with `Network` and `Page` enabled and acknowledged) exists before a page's first request; Playwright's own response events are cross-checked against the records of the same page at the end (`response never captured` fails). Bodies are read when the browser reports the request finished, base64 bodies are decoded and scanned, binary asset types (SVG is text and scanned) and cache-served app assets whose read fails are listed, and a read that fails or never finishes is excused only by a NEW-DOCUMENT commit of its frame (not a history route change, not a navigation that has started: Chromium holds the read until the commit, or answers it when the navigation ends without one) or a closed page (judged on the facts at the failure; after a refused read that nothing else explains, only the close event is awaited within the grace), and then listed. A secret registered with `guard.secret` (also the login-link code `signInWith` uses) is looked for in EVERY response of the test, also those received before it was registered; only the body of the one response declared to carry it (page + method + path, at most once: a token's `POST /api/tokens`) is exempt. An `/api/` body lost while a secret is registered fails unless the flow declares exactly that loss with `guard.allowLostBody(page, method, path, why)` (a new-document loss only). `00-guard-selftest.spec.ts` covers every transition (T1-T9, N2, N3, the scans S, H, U) and that no spec creates a page behind the guard; a leak is also proved through the real network with the control API's `POST /echo`), and a secret shown in a dialog (`guard.secretGone`) absent from the DOM and the storages. Specs take texts from `apps/web/src/strings.ts` and role-based locators. Failed runs keep traces and screenshots in `node_modules/.cache/playwright/flows-results` (`E2E_OUTPUT_DIR`). CI job `e2e-flows` (arm64, after `go`) uploads them with `COMPAT_LOG_DIR`.

## Running locally

- Tests: `pnpm install`, then `pnpm verify`. Docker is required: integration tests start Postgres through Testcontainers.
- Server build: `pnpm build` (`vp pack`) produces `apps/server/dist/main.js` and `dist/cli.js`. The server does not run from sources.
- Full box: `cp .env.example .env`, fill in `POSTGRES_PASSWORD`, `SECRETS_KEY` (`openssl rand -base64 32`) and `OIDC_*`, then `docker compose up -d --build`; check `curl localhost:3000/healthz`.
- Quick start: `quickstart.compose.yml` (project `mcp-registry`, image `${MCP_REGISTRY_IMAGE:-ghcr.io/ai-pipes/mcp-registry:1}`; `docker-compose.yml` is the build-from-source file and never names the published image). Services: `init` (one-shot, generates `secrets_key` and `pg_password` into the `secrets` volume only when absent or empty, files 0444, atomic write), `db` (`POSTGRES_PASSWORD_FILE`; Postgres not published) and `app` (`SECRETS_KEY_FILE`, `PGPASSWORD_FILE`, no OIDC by default: first-start sign-in link in the log). Data is in `pgdata`; `down -v` destroys data and key together, and losing `secrets` while keeping `pgdata` also changes the database password. Optional settings (OIDC, `TRUST_PROXY`, `COOKIE_SECURE`, limits, search, `LOG_LEVEL`...) pass through from the caller's shell or `--env-file` as `NAME: ${NAME:-}` (empty = unset), so shell variables of the same name apply. `SECRETS_KEY`, `DATABASE_URL` and `PGPASSWORD` are owned by the file, except `SECRETS_KEY_OLD` which passes through for key rotation (new key written into the `secrets` volume, old one in `SECRETS_KEY_OLD`; procedure in the README). The port is published as `${BIND_ADDRESS:-127.0.0.1}:${PORT:-3000}:3000` (localhost by default; `BIND_ADDRESS=0.0.0.0` with a real `PUBLIC_URL` behind HTTPS exposes it) and `PUBLIC_URL` defaults to `http://localhost:${PORT:-3000}`. The session cookie stays `Secure` by default: Chrome and Firefox accept it on `http://localhost`, Safari and plain http on a LAN address need `COOKIE_SECURE=false`; anything beyond localhost belongs behind HTTPS. Commands for a stack started from stdin: `docker compose -p mcp-registry logs app | grep "one-time link"` (link), `docker compose -p mcp-registry exec app node dist/cli.js <cmd>`, `docker compose -p mcp-registry down`. `up -d` succeeds even when the app loops on a key mismatch: check `logs app`.
- Quick start smoke test: `bash scripts/quickstart-smoke.sh` (project `mcp-quickstart-smoke`, port 38081, image built from this tree, or `QUICKSTART_IMAGE=<image>` for a prebuilt one that is left in place; also checks the `starting` record and the newer-database refusal; unsets every variable the compose file passes through; compose fed through stdin; one sign-in link in the log, sign-in, token, `/mcp` `tools/list`; restart keeps the token and logs no new link; `compose()` passes `--env-file /dev/null` (a `.env` in the repo root cannot change the run); the documented file-less `login-link` and `logs` through `-p` are exercised; rendered config asserts the pass-through, `127.0.0.1`, `PUBLIC_URL` following `PORT` and the default image; replacing only the key makes the app refuse to start with the fatal text and its README pointer and no key in the log; removes its volumes and image). CI job `quickstart`.
- Image smoke test: `bash scripts/smoke.sh` (`SMOKE_IMAGE=<image>` runs the app from a prebuilt image; separate compose project on port 38080 + `scripts/smoke.compose.yml` with a test upstream, Dockerfile target `smoke-upstream`, `apps/server/test/smoke/upstream.ts`, not in the runtime image; the CLI creates an admin, a token and a `shared_secret` server, `apps/server/test/smoke/mcp-client.ts` runs `search_tools -> describe_tool -> call_tool` and checks the upstream got the secret header while the client and logs never saw it; removes its volume).
