# Contributing

Thanks for helping. Bug reports, fixes and small focused features are welcome. For larger changes, open an issue first to agree on the approach.

## Setup

You need Node 22, pnpm (the version pinned in `package.json`; `corepack enable` picks it up) and Docker (integration tests start Postgres through Testcontainers).

```sh
pnpm install          # also installs lefthook git hooks
pnpm verify           # must be green before you open a PR
```

Optional, for changes that affect the image or the UI end to end:

```sh
bash scripts/smoke.sh        # builds the image, runs CLI -> MCP search -> describe -> call
bash scripts/e2e-image.sh    # Playwright against the built image (pnpm exec playwright install chromium)
```

## How we work

- **`pnpm verify` must pass**: format, lint, types, architecture rules, knip, unit and integration tests, UI build. The pre-push hook runs it; do not skip hooks with `--no-verify`.
- **Tests first.** Write the failing test, then the code. Domain rules get a unit test next to the code; use cases are tested with fake ports; adapters get an integration test against real Postgres (`apps/server/test/**/*.int.test.ts`). Coverage of `domain` and `application` must stay at or above 90%.
- **Respect the architecture.** The server is a modular monolith with DDD layers; import rules are enforced by dependency-cruiser and by architecture tests with failing fixtures, and each module owns its database schema. Read [CLAUDE.md](./CLAUDE.md) before your first change: it lists the layers, the rules, the domain vocabulary and the recipe for a new use case.
- **Never weaken a rule to get green.** No `eslint-disable`, no `@ts-ignore`, no edits to `.dependency-cruiser.cjs` or coverage thresholds, no `it.skip`, no CSP exceptions. Fix the code. If you believe a rule is wrong, propose the change in a separate PR with its reasoning.
- **UI** uses shadcn/ui on Base UI (no Radix); all strings live in `apps/web/src/strings.ts`; the CSP forbids inline scripts and `<style>` elements.
- **Never log secrets, tokens, or call arguments and results.**
- **Changelog.** A change an operator can see (a setting, a CLI command, an upgrade step, a changed default, a fix they would notice) adds a line to `CHANGELOG.md` in the same pull request.
- Keep docs in step: a new module, term, command or environment variable updates `CLAUDE.md`, `README.md` and `.env.example` in the same PR.

## Go rewrite and the compatibility suite

The Go server is being built beside the TypeScript one; `compat/` is the Go black-box suite both must satisfy (details in [CLAUDE.md](./CLAUDE.md), "Go rewrite").

```sh
make go-verify              # Go lint, architecture rules, vet, unit tests (CI job `go`); needs no native library
make native-libs            # downloads the pinned ONNX Runtime and tokenizers libraries for this platform into .cache/native (SHA-256 checked)
make go-verify-onnx         # vet, lint and tests of the code behind the build tag `onnx`, the local embedder (CI job `go-onnx`, arm64 and amd64)
make go-test-onnx-parity    # token ids and vectors of the Go embedder against the reference image's, in containers (needs mcp-registry:compat-ts; run by CI job `compat-go`)
make compat-image-ts        # builds mcp-registry:compat-ts from this tree
make compat                 # the suite against that image (needs Docker, about 11 to 15 minutes: runs took 593-679 s before the second stack of the recorded queries and 647 s and 903 s after it (the host was busy in the second), the packages one after another, `-p 1`; CI job `compat`)
make compat-image-go        # builds mcp-registry:compat-go (Dockerfile target `go`, the Go server)
make compat-go              # the Go image under the scenarios of the milestone list, COMPAT_GO_TESTS minus COMPAT_GO_SKIP (needs both images; CI job `compat-go`, arm64 and amd64, not required)
make compat-selfcheck       # proves the suite fails on a deliberately broken image (daily in CI)
make e2e-flows              # the web UI's browser flows (Playwright, Chromium) against the same image (CI job `e2e-flows`)
```

`make e2e-flows` needs `pnpm install` and `pnpm exec playwright install chromium`. The flows (`e2e/flows/*.spec.ts`) cannot run on their own: the Go test `TestBrowserFlows` (`compat/e2e`) boots the stacks and the fakes and passes a control API (127.0.0.1, per-run bearer token, fixed operations only) to them. A failed run leaves traces and screenshots in `node_modules/.cache/playwright/flows-results` (`pnpm exec playwright show-trace <dir>/trace.zip`). A new flow goes in `e2e/flows/NN-name.spec.ts`, takes texts from `apps/web/src/strings.ts`, uses role-based locators, never waits for a fixed time, and is shown to fail when its expectation is broken.

- **What the image under test must be.** The suite runs an IMAGE: it starts the server with the image's default command (so the image declares `CMD`, not `ENTRYPOINT`: the harness runs the operator CLI in the same image by replacing the command with `COMPAT_CLI` plus the arguments), listening on port 3000 inside the container (the harness publishes it; `PORT` is set only by the one scenario that moves it), configured through the environment variables of `apps/server/src/platform/config.ts`. The database is `pgvector/pgvector:pg17`, started by the harness. It must serve the UI shell on `GET /` (the harness probe after every start asks for it with `Accept: text/html`), and start with its default command. To judge the Go server, build its image with `make compat-image-go` (`mcp-registry:compat-go`, Dockerfile target `go`) and run `make compat-go`; for another image run `COMPAT_IMAGE=<tag> COMPAT_CLI=<cli invocation> make compat`.
- Run against another image with `COMPAT_IMAGE` (default `mcp-registry:compat-ts`) and `COMPAT_CLI` (how the CLI is invoked inside it, default `node dist/cli.js`). To keep the app log of failed tests, set `COMPAT_LOG_DIR=<dir>`; `COMPAT_APP_ENV=NAME=value,...` adds non-secret variables to the app container.
- Other variables: `COMPAT_UPGRADE_FROM` (the image that creates the state in the upgrade scenario, default `COMPAT_IMAGE`; set it to the TypeScript 1.x image (for a real upgrade, `ghcr.io/ai-pipes/mcp-registry:1.0.0`; unset it is a restart test) when `COMPAT_IMAGE` is the Go one) with `COMPAT_UPGRADE_FROM_CLI` (its CLI invocation), `COMPAT_REFERENCE_IMAGE` (see goldens below), `SELFCHECK_BASE` (the image `make compat-selfcheck` derives its broken image from, default `mcp-registry:compat-ts`), `E2E_PLAYWRIGHT_ARGS` (selects flows for `make e2e-flows`, see CLAUDE.md for what is refused) and `COMPAT_ARGS` (extra `go test` arguments for `make compat`).
- **Decided deviations (`COMPAT_FIXED`).** The owner has decided, finding by finding, where the Go server deliberately differs from the reference TypeScript image (currently 1.0.1). The suite judges both images: a scenario that touches a decided deviation has two expectations, `if s.Fixed(harness.DevX) { the decided behaviour } else { the reference behaviour }` (`compat/harness/deviations.go`: the `Deviation` constants, the registry `AllDeviations`, `Stack.Fixed`). `COMPAT_FIXED` selects the decided behaviours: `all`, or a comma-separated list of ids; an unknown id is an error when the stack starts. **Unset means none fixed: the reference TypeScript image runs with it unset and passes through the reference branches, which are never weakened. The Go image is expected to pass with `COMPAT_FIXED=all` at the switchover.** The output of a command whose decided behaviour cannot be recorded from the reference image has no golden: the fixed branch asserts exit code, effect and the texts named in the table. A test checks that every id in `AllDeviations` is used by a scenario file. **A new deviation needs the owner's decision;** never add one (or move a scenario to the fixed branch) to make the Go server pass.

- **The Go image and the milestone pattern.** The Dockerfile has a target `go` (stages `go-native`, `go-build`, `go`: `CGO_ENABLED=1` and `-tags onnx` natively for each architecture, the ONNX Runtime library pinned in `internal/modules/search/infra/onnx/native/pins.env` and installed at `/usr/local/lib/libonnxruntime.so.1`, the model in `/app/models`, `MALLOC_ARENA_MAX=2`, binary `/usr/local/bin/mcp-registry`, UI in `/app/web`, the licence texts in `/usr/share/licenses/mcp-registry/` (`LICENSE` and `THIRD_PARTY_NOTICES`: ONNX Runtime, the tokenizers library, the Go bindings and the model), user 10001, `CMD ["mcp-registry"]`, no `ENTRYPOINT`, no healthcheck yet; the image is about 300 MB); `runtime`, the TypeScript image, stays the last stage and so the default target of `docker build .`. `make compat-image-go` builds `mcp-registry:compat-go` with the version of `apps/server/package.json`. `make compat-go` runs `COMPAT_IMAGE=mcp-registry:compat-go COMPAT_CLI=mcp-registry COMPAT_FIXED=$(COMPAT_GO_FIXED)` over the scenarios named by `COMPAT_GO_TESTS` in the `Makefile` (the milestone list: the scenarios the Go server passes so far; it grows with each milestone, a scenario that needs a route, a person or a command of a later milestone is not in it), without the subtests of `COMPAT_GO_SKIP` (a `go test -skip` expression with one entry per skipped subtest, so several for some scenarios, each naming a subtest of a listed scenario that needs a later milestone; the `Makefile` comment says which milestone removes each). Both variables are set with `:=`: an environment variable does not override them, give them on the make command line (`make compat-go COMPAT_GO_TESTS='TestConfigRefused'`, `make compat-go COMPAT_GO_SKIP=`; `$$` is a literal `$`, and a value must not contain a single quote). Before it runs anything it lists the pattern with `go test -list` (nothing is started) and fails unless exactly as many scenarios match as `COMPAT_GO_TESTS` names, so a renamed or mistyped scenario cannot pass by running nothing. It needs `mcp-registry:compat-ts` as well and fails at once, naming it, when it is missing. `make compat-image-go` fails when the version read from `apps/server/package.json` is empty and, after the build, when the image's `mcp-registry --version` differs from it. The Go image has no `HEALTHCHECK` yet (the TypeScript one has); it needs one before it replaces the published image. `make e2e-flows-go` runs the browser flows that need only identity and the catalog against the Go image (the specs `00` to `02`, `04` to `07`, `10` and `11`, 45 tests, under the unchanged guard; CI job `e2e-flows-go`); the flows that wait for a later milestone are not selected: `03-tokens` and `09-permissions` (a token or a call through `/mcp`, and the call log, milestone 6), `08-connect`, `08b-connect-cross-site` and `12-direct-links` (the connections page and OAuth connect, 5). `make e2e-flows` itself still needs `/mcp` for `TestControlOperationsAgainstARealStack`. Do not add `-run` to `COMPAT_ARGS` of `make compat-go` (a second `-run` replaces the pattern); `-skip` in it adds to nothing (a second `-skip` replaces `COMPAT_GO_SKIP`).
- **A scenario changes only together with confirmation against the reference TypeScript image (currently 1.0.1).** A release of the reference (an owner-approved change of its behaviour) is the one case where a scenario changes to judge the new behaviour: strictly, with the deviation it satisfied removed from the registry. Never edit a scenario or a golden to make the Go server pass; if the Go server differs, the Go server is wrong unless the owner decides otherwise.
- Goldens are rewritten only against the TypeScript reference image: `COMPAT_REFERENCE=1 go test -tags compat ./compat/ -run '<the test that owns it>' -update`. `-update` is refused unless `COMPAT_REFERENCE=1` AND the image under test is the reference image: the built-in default tag, or exactly the value of `COMPAT_REFERENCE_IMAGE` when that is set (CI can name its reference image this way). `make compat` sets neither, so `COMPAT_IMAGE=<go image>` with `-update` is refused. `-update` rewrites every golden of the tests it runs, so restrict it with `-run`.
- Vectors and rankings have no committed golden: q8 vectors differ between CPUs of the same architecture by up to about 0.015, so `TestSearchStoredVectors` and `TestCatalogSearch/the_recorded_queries` compare the image under test with the reference image on the same machine. The reference image is `COMPAT_REFERENCE_IMAGE`, else `mcp-registry:compat-ts`, and it must exist locally when another image is under test (`make compat-image-ts`; the tests fail naming it otherwise). The vectors come from `compat/golden/gen-embeddings.mjs` run with `@huggingface/transformers` inside a container of the reference image (no network); the queries are asked of a second stack booted from it. With the reference image under test both are determinism checks; with the Go image they are the real comparison. A few queries with CPU-independent first hits are also asserted as literals.
- A new check in the suite should have a matching distortion in `compat/selfcheck` when it guards a property a broken server could plausibly lose.

## Releasing

1. Rehearse: `gh workflow run release --ref <branch>` (once the workflow file with the `workflow_dispatch` trigger is on `main`) and wait for a green result. A pull request that touches the release path (workflow, Dockerfile, compose files, smoke scripts, lockfile, the version in `apps/server/package.json`, `CHANGELOG.md`) rehearses automatically. A rehearsal builds and tests everything (both architectures, both smoke tests) but never publishes and needs no secrets.
2. Date the changelog entry (`## [<version>] - YYYY-MM-DD`; `Unreleased` blocks the release) and add the compare link at the bottom.
3. Make sure `apps/server/package.json` has the version (the only place it is set), and update the two places that pin the release tag: the quick-start command in `README.md` and the usage line in the header of `quickstart.compose.yml`.
4. Before tagging, confirm the rehearsal on the release-prep pull request is green and shows no warning from the strict check ("a tag ... pushed now would be refused").
5. Merge to `main`.
6. Tag `v<version>` on `main` and push the tag. The release workflow checks the tag, the changelog entry and that the commit is on `main`, builds the image, tests it (version printed by the amd64 and arm64 images, quick-start smoke, compose smoke) and only then pushes it to GHCR.
7. After the workflow finishes, confirm an anonymous pull works (`docker logout ghcr.io; docker pull ghcr.io/ai-pipes/mcp-registry:<version>`) and that the package is public and linked to the repository.

## Commits

[Conventional Commits](https://www.conventionalcommits.org/), as in the git log:

```
feat(mcp): own body limit for /mcp, MCP_MAX_BODY_BYTES (default 10 MiB)
fix(http): browser callbacks redirect with 'internal' on unexpected errors
refactor(catalog): sync owner rule into catalog
docs: ...
```

Types: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `ci`, `build`, `perf`. The scope is the module or area (`identity`, `catalog`, `connections`, `search`, `gateway`, `mcp`, `http`, `web`, `cli`...). Use the imperative mood and keep the subject short.
