# Contributing

Thanks for helping. Bug reports, fixes and small focused features are welcome. For larger changes, open an issue first to agree on the approach.

## Setup

You need Node 22, pnpm (the version pinned in `package.json`; `corepack enable` picks it up) and Docker (integration tests start Postgres through Testcontainers).

```sh
pnpm install          # also installs lefthook git hooks
pnpm verify           # must be green before you open a PR
```

Optional, for changes that affect the image or the UI end to end:

```sh
bash scripts/smoke.sh        # builds the image, runs CLI -> MCP search -> describe -> call
bash scripts/e2e-image.sh    # Playwright against the built image (pnpm exec playwright install chromium)
```

## How we work

- **`pnpm verify` must pass**: format, lint, types, architecture rules, knip, unit and integration tests, UI build. The pre-push hook runs it; do not skip hooks with `--no-verify`.
- **Tests first.** Write the failing test, then the code. Domain rules get a unit test next to the code; use cases are tested with fake ports; adapters get an integration test against real Postgres (`apps/server/test/**/*.int.test.ts`). Coverage of `domain` and `application` must stay at or above 90%.
- **Respect the architecture.** The server is a modular monolith with DDD layers; import rules are enforced by dependency-cruiser and by architecture tests with failing fixtures, and each module owns its database schema. Read [CLAUDE.md](./CLAUDE.md) before your first change: it lists the layers, the rules, the domain vocabulary and the recipe for a new use case.
- **Never weaken a rule to get green.** No `eslint-disable`, no `@ts-ignore`, no edits to `.dependency-cruiser.cjs` or coverage thresholds, no `it.skip`, no CSP exceptions. Fix the code. If you believe a rule is wrong, propose the change in a separate PR with its reasoning.
- **UI** uses shadcn/ui on Base UI (no Radix); all strings live in `apps/web/src/strings.ts`; the CSP forbids inline scripts and `<style>` elements.
- **Never log secrets, tokens, or call arguments and results.**
- **Changelog.** A change an operator can see (a setting, a CLI command, an upgrade step, a changed default, a fix they would notice) adds a line to `CHANGELOG.md` in the same pull request.
- Keep docs in step: a new module, term, command or environment variable updates `CLAUDE.md`, `README.md` and `.env.example` in the same PR.

## Go rewrite and the compatibility suite

The Go server is being built beside the TypeScript one; `compat/` is the Go black-box suite both must satisfy (details in [CLAUDE.md](./CLAUDE.md), "Go rewrite").

```sh
make go-verify              # Go lint, architecture rules, vet, unit tests (CI job `go`); needs no native library
make go-cover               # the coverage gate: domain and app of every module >= 90 % of statements, per package, from unit tests (part of go-verify)
make native-libs            # downloads the pinned ONNX Runtime and tokenizers libraries for this platform into .cache/native (SHA-256 checked)
make go-verify-onnx         # vet, lint and tests of the code behind the build tag `onnx`, the local embedder (CI job `go-onnx`, arm64 and amd64)
make go-test-onnx-parity    # token ids and vectors of the Go embedder against the reference image's, in containers (needs the reference, make compat-reference; run by CI job `compat-go`)
make compat-reference       # pulls the reference, the published TypeScript 1.0.1 pinned by digest (REFERENCE_IMAGE in the Makefile), and checks the digest
make compat-image-ts        # builds mcp-registry:compat-ts from this tree (the default image under test until the switchover)
make compat                 # the suite against that image (needs Docker, about 11 to 15 minutes: runs took 593-679 s before the second stack of the recorded queries and 647 s and 903 s after it (the host was busy in the second), the packages one after another, `-p 1`; CI job `compat` runs it with the reference under test: make compat COMPAT_IMAGE="$(make -s print-reference-image)")
make compat-image-go        # builds mcp-registry:compat-go (Dockerfile target `go`, the Go server)
make compat-go              # the Go image under the scenarios of the milestone list, COMPAT_GO_TESTS minus COMPAT_GO_SKIP (needs the Go image and the reference; CI job `compat-go`, arm64 and amd64, not required)
make compat-selfcheck       # proves the suite fails on a deliberately broken image (daily in CI)
make e2e-flows              # the web UI's browser flows (Playwright, Chromium) against the same image (CI job `e2e-flows`)
```

`make e2e-flows` needs `pnpm install` and `pnpm exec playwright install chromium`. The flows (`e2e/flows/*.spec.ts`) cannot run on their own: the Go test `TestBrowserFlows` (`compat/e2e`) boots the stacks and the fakes and passes a control API (127.0.0.1, per-run bearer token, fixed operations only) to them. A failed run leaves traces and screenshots in `node_modules/.cache/playwright/flows-results` (`pnpm exec playwright show-trace <dir>/trace.zip`). A new flow goes in `e2e/flows/NN-name.spec.ts`, takes texts from `apps/web/src/strings.ts`, uses role-based locators, never waits for a fixed time, and is shown to fail when its expectation is broken.

- **What the image under test must be.** The suite runs an IMAGE: it starts the server with the image's default command (so the image declares `CMD`, not `ENTRYPOINT`: the harness runs the operator CLI in the same image by replacing the command with `COMPAT_CLI` plus the arguments), listening on port 3000 inside the container (the harness publishes it; `PORT` is set only by the one scenario that moves it), configured through the environment variables of `apps/server/src/platform/config.ts`. The database is `pgvector/pgvector:pg17`, started by the harness. It must serve the UI shell on `GET /` (the harness probe after every start asks for it with `Accept: text/html`), and start with its default command. To judge the Go server, build its image with `make compat-image-go` (`mcp-registry:compat-go`, Dockerfile target `go`) and run `make compat-go`; for another image run `COMPAT_IMAGE=<tag> COMPAT_CLI=<cli invocation> make compat`.
- Run against another image with `COMPAT_IMAGE` (default `mcp-registry:compat-ts`) and `COMPAT_CLI` (how the CLI is invoked inside it, default `node dist/cli.js`). To keep the app log of failed tests, set `COMPAT_LOG_DIR=<dir>`; `COMPAT_APP_ENV=NAME=value,...` adds non-secret variables to the app container.
- Other variables: `COMPAT_UPGRADE_FROM` (the image that creates the state in the upgrade scenario, default `COMPAT_IMAGE`; set it to the TypeScript 1.x image (for a real upgrade, the published 1.0.0: `"$(make -s print-upgrade-from-image)"`, pulled by `make compat-upgrade-from`; unset it is a restart test; `make compat-go` sets it to that image itself, see below) with `COMPAT_UPGRADE_FROM_CLI` (its CLI invocation), `COMPAT_REFERENCE_IMAGE` (see goldens below), `SELFCHECK_BASE` (the image `make compat-selfcheck` derives its broken image from, default the reference image), `E2E_PLAYWRIGHT_ARGS` (selects flows for `make e2e-flows`, see CLAUDE.md for what is refused) and `COMPAT_ARGS` (extra `go test` arguments for `make compat`).
- **Decided deviations (`COMPAT_FIXED`).** The owner has decided, finding by finding, where the Go server deliberately differs from the reference TypeScript image (currently 1.0.1). The suite judges both images: a scenario that touches a decided deviation has two expectations, `if s.Fixed(harness.DevX) { the decided behaviour } else { the reference behaviour }` (`compat/harness/deviations.go`: the `Deviation` constants, the registry `AllDeviations`, `Stack.Fixed`). `COMPAT_FIXED` selects the decided behaviours: `all`, or a comma-separated list of ids; an unknown id is an error when the stack starts. **Unset means none fixed: the reference TypeScript image runs with it unset and passes through the reference branches, which are never weakened. The Go image is expected to pass with `COMPAT_FIXED=all` at the switchover.** The output of a command whose decided behaviour cannot be recorded from the reference image has no golden: the fixed branch asserts exit code, effect and the texts named in the table. A test checks that every id in `AllDeviations` is used by a scenario file. **A new deviation needs the owner's decision;** never add one (or move a scenario to the fixed branch) to make the Go server pass.

- Goldens are rewritten only against the TypeScript reference image: `COMPAT_IMAGE="$(make -s print-reference-image)" COMPAT_REFERENCE=1 go test -tags compat ./compat/ -run '<the test that owns it>' -update`. `-update` is refused unless `COMPAT_REFERENCE=1` AND the image under test is the reference image: the published 1.0.1 pinned by digest (`COMPAT_IMAGE="$(make -s print-reference-image)"`; the default image under test, `mcp-registry:compat-ts`, is not the reference), or exactly the value of `COMPAT_REFERENCE_IMAGE` when that is set, which must then be pinned by digest (`<name>@sha256:<64 hex>`; a tag alone is refused). `make compat` sets neither, so `COMPAT_IMAGE=<go image>` with `-update` is refused. `-update` rewrites every golden of the tests it runs, so restrict it with `-run`.

The reference image is `COMPAT_REFERENCE_IMAGE`, else the published TypeScript 1.0.1 pinned by the digest of its multi-arch index (`defaultReferenceImage` in `compat/harness/stack.go`, `REFERENCE_IMAGE` in the `Makefile`, the default base of `compat/selfcheck/Dockerfile`; a Docker-free test keeps the three equal; its CLI is `node dist/cli.js`), and it must exist locally: the harness never pulls, `make compat-reference` does and checks the digest (the tests fail naming it otherwise). The vectors come from `compat/golden/gen-embeddings.mjs` run with `@huggingface/transformers` inside a container of the reference image (no network); the queries are asked of a second stack booted from it. With the reference image under test both are determinism checks; with the Go image they are the real comparison. A few queries with CPU-independent first hits are also asserted as literals.
- A new check in the suite should have a matching distortion in `compat/selfcheck` when it guards a property a broken server could plausibly lose.

## Load comparison

`make load-compare` boots one stack per image, one after another, and reports a Markdown table (stdout and `LOAD_OUT`, default a file under the system temp dir). It needs the two images: A, the published 1.0.0 pinned by digest (`make compat-upgrade-from`), and B, the Go image (`make compat-image-go`); `LOAD_IMAGE_A`, `LOAD_CLI_A`, `LOAD_IMAGE_B`, `LOAD_CLI_B` and `LOAD_FIXED_B` (default `COMPAT_GO_FIXED`) override them. It runs `compat/load_test.go` (build tags `compat load`: neither `make compat` nor `go-verify` runs it, `go-verify` only vets it) and takes about 3 minutes. It reports and asserts nothing; it fails only when a stack does not boot or an image answers an error while nothing else runs.

Same fixtures for both: the recorded Gitea and YouTrack tools (84 indexed documents) and an echo tool on a fake upstream that holds each call for 5 ms, one admin, one `sk_` token, no daily limit (none is set by default) and no rate limit on valid tokens. Measured after a warm-up: idle memory (`docker stats`, three samples 30 s after the warm-up), sequential latency (200 `search_tools` over 18 rotating queries and 200 `call_tool`, one reused session, p50/p95/max), and 5 rounds of 50 concurrent calls of each (errors, percentiles, peak memory from a roughly 1 Hz `docker stats` stream, and one `/healthz` probe per round for event-loop responsiveness). Raw numbers depend on the CPU and are not committed.

Two runs, on 2026-11-27, on a shared developer laptop (Apple M1 Pro, 10 CPUs, Docker 29.4.0 with a 10 CPU / 8 GB VM, other containers running, load average about 8; both images linux/arm64). A is the published TypeScript 1.0.0 (`sha256:9966fa11e597b45fe27ad916b4121a312c624232a1855d922c1f1946f7c09d72`), B the Go image built from this tree (image id `sha256:79e044ae527f`). Each cell is A vs B.

Run-to-run differences are large on this machine: between the two runs the 50-concurrent `call_tool` p95 moved from 311 to 511 ms (A) and from 78 to 137 ms (B), A's `/healthz` median during the search rounds from 126 to 83 ms, and A's concurrent search p95 from 1067 to 740 ms; only large gaps (the concurrent `call_tool` figures, `/healthz` under search, A's higher memory) held in both runs, while the sequential figures overlap. ## Third-party notices

The Go image ships the licence texts of everything it redistributes in `/usr/share/licenses/mcp-registry/`: `THIRD_PARTY_NOTICES` (the hand-written overview) and the generated files under `third_party/`. Regenerate them from the repository root when what they describe changes; the tests in `tools/notices` (part of `go test ./...` and so of `make go-verify`) fail until you do:

- A Go dependency changes (`go.mod`): `go run ./tools/notices go` (offline once the module cache has the modules, `go mod download`).
- A dependency of the web UI changes (`apps/web/package.json`, the lockfile): `pnpm install`, then `go run ./tools/notices web`. The file records a hash of the lockfile entries it was made from, so a transitive change fails too. A Dependabot pull request of either kind stays red until a maintainer pushes the regenerated file to it.
- The ONNX Runtime pin changes (`pins.env`): set `ORT_NOTICES_WHEEL_URL` and `ORT_NOTICES_WHEEL_SHA256` to a PyPI wheel of the same release (any platform: the two text files are the same), then `go run ./tools/notices onnxruntime`.
- The tokenizers pin changes (`pins.env`): `git clone --depth 1 --branch v<version> https://github.com/daulet/tokenizers <dir>`, then `go run ./tools/notices rust <dir>` (needs `cargo`, which downloads the crate sources).

Nothing is downloaded at image build time. A component that is not covered by a generated file (a new kind of native dependency, a crate without a licence file) gets an entry in `THIRD_PARTY_NOTICES` by hand.

## Releasing

1. Rehearse: `gh workflow run release --ref <branch>` (once the workflow file with the `workflow_dispatch` trigger is on `main`) and wait for a green result. A pull request that touches the release path (workflow, Dockerfile, compose files, smoke and release scripts, lockfiles, the Go sources and `go.mod`, the notices, the `VERSION` file, `CHANGELOG.md`) rehearses automatically. A rehearsal builds and tests everything on both architectures, each on its own native runner (`--version`, both smoke tests), and assembles a manifest list with `--dry-run`, but never publishes and needs no secrets.
2. Date the changelog entry (`## [<version>] - YYYY-MM-DD`; `Unreleased` blocks the release) and add the compare link at the bottom.
3. Make sure the `VERSION` file has the version (the only place it is set; `apps/server/package.json` must say the same until it is deleted), and update the two places that pin the release tag: the quick-start command in `README.md` and the usage line in the header of `quickstart.compose.yml`.
4. Before tagging, confirm the rehearsal on the release-prep pull request is green and shows no warning from the strict check ("a tag ... pushed now would be refused").
5. Merge to `main`.
6. Tag `v<version>` on `main` and push the tag. The release workflow checks the tag, the changelog entry and that the commit is on `main`, builds the image natively on an amd64 and an arm64 runner and tests each (version printed by the image, quick-start smoke, compose smoke), and only then pushes each architecture by digest (refused unless its layers are the tested ones) and merges the two into one manifest list under the tags (`<major>.<minor>.<patch>`, `<major>.<minor>`, `<major>`, `latest`), checked to hold exactly those two images. If the push step reports that the pushed image is not the tested one (the build cache was evicted), re-run all jobs, not only the failed ones.
7. After the workflow finishes, confirm an anonymous pull works (`docker logout ghcr.io; docker pull ghcr.io/ai-pipes/mcp-registry:<version>`) and that the package is public and linked to the repository.

## Commits

[Conventional Commits](https://www.conventionalcommits.org/), as in the git log:

```
feat(mcp): own body limit for /mcp, MCP_MAX_BODY_BYTES (default 10 MiB)
fix(http): browser callbacks redirect with 'internal' on unexpected errors
refactor(catalog): sync owner rule into catalog
docs: ...
```

Types: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `ci`, `build`, `perf`. The scope is the module or area (`identity`, `catalog`, `connections`, `search`, `gateway`, `mcp`, `http`, `web`, `cli`...). Use the imperative mood and keep the subject short.

## Pull request checklist

- [ ] `pnpm verify` is green locally.
- [ ] New behaviour is covered by tests written first; bug fixes include a regression test.
- [ ] No architecture, lint or coverage rule was weakened.
- [ ] No secrets, tokens or call payloads are logged or returned to clients.
- [ ] `CLAUDE.md`, `README.md` and `.env.example` are updated if behaviour, configuration or vocabulary changed.
- [ ] Database changes come as a new migration in `apps/server/migrations` (never edit an applied one) and stay inside the module's own schema.
